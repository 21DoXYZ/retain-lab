## 0. Где мы сейчас одной картинкой

```
CSV-выгрузки (руками)
  → ClickHouse raw (users, money_transactions, game_transactions, game_sessions)
  → player_features.sql (фичи)  → marts.sql (витрины + пустые ML-таблицы)
  → train_all.sh (CatBoost, руками) → предсказания в player_*_ml
  → player_board.py (Flask, read-only) → дашборд
```

Это **разовый batch/offline-пайплайн**. Работает, но «само не крутится»: запуск руками,
модели не сохраняются в файлы, нет расписания/версионирования/мониторинга, данные с обрезкой
(cutoff в дампе). Ниже — куда это эволюционирует.

## 1. Сервинг ML: как модель должна «крутиться и предиктить»

### Сейчас — batch-скоринг руками ✅/🟡
`*_model.py` обучает CatBoost в памяти, пишет предсказания в таблицу, **выбрасывает модель**.
Пробелы: ❌ модели нигде не сохраняются (нет `.cbm`), ❌ запуск руками, ❌ нет версий
(какая модель посчитала строку и когда — неизвестно), ❌ нет мониторинга деградации.

### Целевое — scheduled batch + registry + monitoring ❌

```
┌──────────────── ClickHouse (single source of truth) ───────────────┐
│ raw → player_features → player_*_ml (+ model_version, scored_at)     │
│ monitoring: model_metrics, prediction_log                           │
└───▲───────────────────▲──────────────────────▲─────────────────────┘
    │                   │                      │
┌───┴────┐        ┌─────┴─────┐         ┌──────┴──────┐
│ TRAIN   │        │ SCORE      │         │ SERVE       │
│ редко   │        │ часто      │         │ дашборд     │
│ weekly  │        │ nightly    │         │ Flask R/O   │
│ → .cbm  │─model─►│ грузит .cbm│         └─────────────┘
│ registry│        │ predict всех│
└─────────┘        └────────────┘
     ▲                   ▲
     └── orchestrator (systemd timer / cron) ──┘
                  │
            MONITORING (drift, метрики, свежесть)
```

**Ключевая идея — разделить TRAIN и SCORE:**
- `TRAIN` (раз в неделю): обучить → **сохранить `.cbm`** (`models/ltv/vYYYYMMDD.cbm` + `latest`) + метрики в `model_metrics`. Дорого, редко.
- `SCORE` (ночью): загрузить `latest.cbm` → `predict` всех → записать в `player_*_ml` с `model_version`/`scored_at`. Дёшево (без обучения), часто.

**Три способа предиктить** (выбор под кейс):

| Паттерн | Latency | Подходит нам |
|---|---|---|
| Batch scoring (по расписанию) | минуты-часы | ✅ основной — LTV/churn меняются медленно |
| Event-driven (по событию игрока) | секунды | 🟡 опц., для свежести (см. §3) |
| Online API (модель-сервис) | мс | ❌ оверкилл для дашборда |

**Пробелы → что добавить:** сохранять `.cbm`; разбить `*_model.py` на `train_*` + `score_*`;
добавить колонки `model_version`/`scored_at`; повесить score на cron, train на weekly;
таблица `model_metrics` + страница `/models`; простой drift-чек (PSI/KS по фичам).

> Перенос обученного состояния между серверами без переобучения уже сделан:
> `dump_ml_tables.sh` / `restore_ml_tables.sh` (см. [SETUP.md](SETUP.md) §5c, Путь Б).

## 2. Приём данных: если источник НЕ на ClickHouse

**Принцип:** неважно, на чём сидит источник (MySQL/PG/Mongo/Kafka/чужой API).
Важен **контракт обмена**, а не тип их БД. Источник развязан с нашим ClickHouse через формат.

```
ЧУЖИЕ СИСТЕМЫ ──► INGESTION (слой загрузки) ──► НАШ ClickHouse (raw) ──► features → ML → дашборд
(их зона)          по контракту                  (наша зона)
```

**Контракт = 5 договорённостей:** схема (поля/типы/ключи) · формат (Parquet ✅ лучше, CSV, JSON,
прямой доступ к БД) · канал доставки · частота · полнота (full vs инкремент).

**Спектр способов передачи:**

| Способ | Кто инициирует | Свежесть | Когда |
|---|---|---|---|
| Файлы в object storage (S3/R2) | они кладут | часы | 🟢 классика, минимум связности |
| Прямой pull из их БД (read-реплика) | мы тянем | минуты-часы | 🟢 если дали доступ |
| CDC / стриминг (Debezium→Kafka) | поток | секунды | 🟡 нужна near-real-time |
| Их push в наш API | они шлют | секунды | 🟡 если у них нет экспорта |
| Ручной CSV | они выгружают | дни | 🔴 только старт (как сейчас) |

**ClickHouse тянет почти откуда угодно сам** — отдельный тяжёлый ETL обычно не нужен:
```sql
INSERT INTO retention.users      SELECT * FROM mysql('host:3306','db','users','ro','pw') WHERE updated_at > {wm};
INSERT INTO retention.money_transactions SELECT * FROM postgresql('host:5432','db','tx','ro','pw','schema');
INSERT INTO retention.game_transactions  SELECT * FROM s3('https://bucket/exports/tx_2026-06-20.parquet','Parquet');
-- стрим: ENGINE = Kafka (kafka_topic_list=...) + Materialized View в обычную таблицу
```

**Рекомендованный дефолт под нас:** они дампят **Parquet-инкремент в object storage**, мы по
крону забираем в raw (вариант А, нулевая связность); либо **прямой pull из read-реплики** (вариант Б).
Real-time (Debezium→Kafka) — только если нужна секундная свежесть.

**Обязательно в слое загрузки:** landing/raw-зона (сырьё как есть, потом маппинг в нашу схему) ·
инкремент по watermark (`WHERE created_at > max(created_at)`) · идемпотентность
(`ReplacingMergeTree` или переналив партиций) · валидация на границе (бьётся с `verify_data.py`) ·
маппинг их `user_id` → наш `casino_player_id` в одном месте.

**Стыковка:** слой загрузки наполняет те же 4 raw-таблицы → дальше всё как сейчас. Меняется
только «как наполняются raw»: вместо `migrate_to_server.sh` руками — по контракту по расписанию.

## 3. Real-time трекинг игроков во время игр

### Сейчас — `/live` это псевдо-live 🟡
Страница `/live` «Играют сейчас» ([player_board.py:1021](player_board.py#L1021)) задумана верно
(онлайн + выигрывает/проигрывает → подсказка действия), но:

| Выглядит как live | На самом деле |
|---|---|
| Обновление каждые 20 сек | `<meta http-equiv="refresh">` — перезагрузка всей страницы, не стрим |
| «Сейчас играют» | «сейчас» = `max(created_at)` в **статичной выгрузке** (cutoff), не стена часов |
| Триггеры действий | только показываются оператору, ничего не срабатывает само |

**3 пробела:** данные не текут (батч, не поток) · «сейчас» ненастоящее · доставка не push, нет автодействия.

### Целевое — стрим-контур ❌

```
игровая платформа ──события: bet/win/session_start/session_end──►
  Kafka / Redpanda
   → ClickHouse (Kafka engine + Materialized View) → live_events / live_state (за секунды)
   → горячее состояние (Redis: текущая сессия, net, серия проигрышей)
   → TRIGGER ENGINE (consumer Python/Go): на каждое событие правило/model.predict() → next-best-action
        ├─► SSE/WebSocket → дашборд /live        (МОНИТОРИНГ)
        └─► offer engine (player_offers) + CRM/бонус-API  (ИНТЕРВЕНЦИЯ)
```

**5 компонентов:** поток событий (это §2, но в стрим-режиме) · стрим-ингест (`Kafka` engine + MV) ·
горячее состояние (Redis для скорости, ClickHouse для аналитики) · trigger engine (правило/CatBoost-предикт
одного игрока — мс) · доставка (SSE в дашборд + опц. авто-бонус).

**Два вкуса — решить, что нужно:**

| | Real-time **мониторинг** | Real-time **интервенция** |
|---|---|---|
| Что делает | показывает «кто играет сейчас» вживую | сам фаерит кэшбэк/бонус по событию |
| Сложность | средняя (стрим → live-таблица → SSE) | высокая (правила/модель в потоке + интеграция с бонус-системой) |
| Нужно от «других» | поток событий | поток событий **+ API на запуск бонуса** |
| Ценность | оператор видит и реагирует руками | авто next-best-action = деньги |

**Переиспользуем:** UX `/live` (меняем только источник: батч+refresh → стрим+SSE) ·
`player_offers` (туда trigger engine логирует авто-действия, [player_board.py:753](player_board.py#L753)) ·
те же `.cbm` модели (предикт одного игрока в потоке).

## 4. Сводный роадмап (эволюция batch → живая система)

| Фаза | Что | Ценность |
|---|---|---|
| **ML-1** | сохранять `.cbm`, разбить train/score, `model_version`/`scored_at`, nightly cron | модель «крутится и предиктит сама» |
| **ML-2** | таблица `model_metrics` + страница `/models` + drift-чек | видно здоровье моделей |
| **DATA-1** | контракт данных с источником + ingestion по расписанию в raw (Parquet/pull) | данные текут без ручного CSV |
| **RT-0** | бейдж «данные на {cutoff}» на `/live` | не путать псевдо-live с live |
| **RT-1** | стрим-ингест: платформа → Kafka → ClickHouse `live_events` | «сейчас» = реально сейчас |
| **RT-2** | SSE/WebSocket вместо 20-сек refresh | `/live` оживает по-настоящему |
| **RT-3** | trigger engine → пишет рекомендации в `player_offers` | next-best-action оператору |
| **RT-4** | авто-интервенция: trigger engine дёргает бонус-API источника | автоматические действия |

Что НЕ нужно при текущем масштабе: online-сервис модели, Airflow/Prefect, feature store, MLflow —
cron + ClickHouse + `.cbm` закрывают всё. Берём сложное только когда упрёмся.
