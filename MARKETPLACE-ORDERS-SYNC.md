# Синк заказов маркетплейсов как источник предиктора (спека, драфт 2026-08-26)

Дополнение к REPLENISHMENT-AUTOPILOT.md. Задача: заказы клиента тенанта на
Shopee / TikTok Shop / Tokopedia становятся топливом предиктора потребления
и базой для капчи клиента в WhatsApp.

## Что уже есть (в стеке SimbaGo, переносимо)

- backend/apps/marketplace: ChannelAccount (Shopee + TikTok, Tokopedia через
  адаптер TikTok, шифрованные токены), маппинг категорий, канальные
  изображения, синк карточек. Django - источник правды.
- Чего НЕТ: пулл заказов с площадок в нашу базу (сейчас товарный синк).

## Ограничение, вокруг которого всё строится

Площадки маскируют контакты покупателя (Shopee маскирует имя/телефон,
Lazada с 2026-07 шифрует через API). Значит:

1. Заказ с площадки даёт ТОЛЬКО: внешний order_id, sku, qty, суммы, дату,
   маскированный buyer-идентификатор площадки (стабильный внутри площадки).
2. Контакт (WhatsApp) появляется ТОЛЬКО через капчу: QR-вкладыш в посылку
   с подписанной wa.me-ссылкой (см. QR-CAPTURE ниже). До капчи покупатель -
   анонимная identity.

## Модель

- Каждый заказ площадки -> серверное событие `mp_order` в saas.events:
  client_user_id = `mp:<channel>:<buyer_id_площадки>` (стабильный псевдоним),
  meta: {channel, external_order_id, items:[{sku, qty, price}], status}.
- Склейка R4 уже создаёт identity по client_user_id без email - анонимный
  покупатель площадки видим в стадиях и планах с первого заказа.
- Капча: покупатель сканирует QR из посылки -> входящее с подписанным кодом
  (парсинг connect-кода уже есть: parse_connect_text) -> привязка
  client_user_id `mp:...` к WhatsApp-номеру + событие согласия -> с этого
  момента у identity есть канал, и replenishment_due может писать ему.
- Реордер у маркетплейс-покупателя: ссылка ведёт на СВОЙ чекаут тенанта
  (маржа без комиссии площадки) - это и есть монетизация капчи.

## Реализация пулла (на стороне тенанта, паттерн SimbaGo)

- Celery-задача каждые 15 мин: для каждого активного ChannelAccount
  тянуть новые/изменённые заказы (Shopee order API v2 get_order_list,
  TikTok Shop orders/search), инкрементально по update_time, идемпотентно
  по (channel, external_order_id).
- Статусы: план потребления создаётся только по COMPLETED/доставлен
  (у площадок высокий процент отмен до выкупа).
- Отправка в платформу: те же серверные события в /ingest/saas/events
  с ingest-токеном тенанта (батчами).

## QR-CAPTURE (вкладыш)

- WMS при печати упаковочного листа для заказа с площадки добавляет блок:
  QR = wa.me/<номер тенанта>?text=<подписанный код с client_user_id mp:...>
  + одна строка выгоды («Скидка/бонус на следующий заказ - жмите и
  получите» - оффер из каталога тенанта, роль activation).
- Код подписан (HMAC, тот же механизм connect_url), TTL не ставим
  (посылка едет днями).
- Метрика: capture rate = привязок / отгруженных вкладышей (события
  telegram_connect_clicked-аналог: wa_connect_scanned).

## Не делаем в v1

- Lazada (API шифрует всё - ценность пулла падает; отложено).
- Пуш-синк остатков/цен в обратную сторону (это территория Jubelio/Ginee,
  красный океан - см. JTBD-ресёрч).
- Автоответы покупателям площадки в чатах площадки.

## Порядок работ

1. Пулл заказов Shopee -> mp_order события (тенант SimbaGo как стенд).
2. R4-склейка и планы на анонимных identity (платформа уже умеет).
3. QR-вкладыш в WMS-печать + capture-флоу.
4. TikTok Shop пулл.
5. Дашборд капчи: отгружено вкладышей / сканов / привязок / реордеров.
