# 1-06 | Discovery Sprint — Справочник структуры

> Reference-документ: что Claude генерирует для предложения Discovery Sprint клиенту.
> Используйте для валидации результата и формулирования требований — не для ручного заполнения.

---

## Философия этого документа

**Вы не пишете предложение Discovery Sprint вручную.** После Discovery Call (1-05) вы передаёте Claude AI контекст клиента — компания, проблема, данные, бюджет — а Claude генерирует полное предложение со сметой, таймлайном, deliverables и примером для TaskFlow-стиля проекта.

Зачем тогда этот справочник?

1. **Валидация** — понять, все ли разделы Claude заполнил (цель, конвейер, смета, таймлайн, метрики)
2. **Корректировка** — если гипотеза размыта или цена не соответствует сложности — знать как попросить переписать
3. **Коммуникация** — говорить с Claude на языке "усиль раздел Дальнейшее движение" вместо "это не то"
4. **Контроль качества** — убедиться, что предложение убедительно для клиента и защищает вас от недопониманий

**Правильный workflow:**
```
Вы → Discovery Call → собрали контекст клиента (проблема, данные, бюджет, гипотеза)
Claude AI → генерирует предложение Discovery Sprint по этому формату
Вы → используете этот справочник чтобы валидировать результат
Claude → дорабатывает разделы по вашим замечаниям
Вы → отправляете клиенту на утверждение
```

---

## Описание

Discovery Sprint — это платный мини-проект, который решает главную проблему заказной разработки: **клиент и разработчик по-разному понимают задачу.**

Вместо того чтобы тратить 2-3 месяца на разработку MVP, а потом выяснить что "это не то" — вы за 1-2 недели собираете работающий прототип на реальных данных клиента, проверяете ключевую гипотезу и фиксируете точные критерии приёмки.

### Что получает клиент:

1. **Работающий прототип** — не макет, а система, в которую можно загрузить данные и получить результат
2. **Отчёт о жизнеспособности** — подтверждение что задача решается технически
3. **Спецификация MVP** — полный документ с архитектурой, экранами, API
4. **Acceptance Criteria** — чёткие критерии приёмки для каждого компонента
5. **Детальная смета** — точная стоимость и сроки (не вилка, а конкретные цифры)

### Почему это работает:

- **Клиент видит результат до основной оплаты** — снижает страх "отдать деньги и не получить ничего"
- **Вы понимаете реальный скоуп** — после Discovery ваша смета точная, а не "от 300K до 1.5M"
- **Прототип не выбрасывается** — код и архитектура переходят в MVP как основа
- **Фильтрует проблемных клиентов** — если клиент не готов заплатить за Discovery Sprint, он не готов к проекту

---

## Когда использовать

- После успешного Discovery Call (документ 1-05), когда клиент квалифицирован
- Для проектов с бюджетом от 300K руб. (Discovery Sprint окупается)
- Когда есть техническая неопределённость (AI, сложные интеграции, нестандартная логика)
- Когда клиент работал с другими подрядчиками и разочарован (Discovery Sprint восстанавливает доверие)

### Когда НЕ нужен:

- Простой лендинг или Telegram-бот (можно сразу сделать)
- Типовой проект без неизвестных (интернет-магазин по шаблону)
- Бюджет клиента менее 100K руб. на весь проект

## Чек-лист валидации (после генерации)

Когда Claude сгенерировал предложение Discovery Sprint — пройдитесь по этому чек-листу. Если что-то не так, попросите Claude доработать конкретный раздел.

```
[ ] 1. Гипотеза сформулирована в одном предложении (не размыта)
[ ] 2. Привязка к реальным данным клиента ("на ваших 20 клиентах")
[ ] 3. Конвейер отрисован со стрелками (вход → обработка → результат → верификация)
[ ] 4. 5 deliverables — каждый имеет самостоятельную ценность для клиента
[ ] 5. Смета соответствует сложности (80-150K простой / 150-250K средний / 250-400K сложный)
[ ] 6. Указаны условия оплаты и срок
[ ] 7. Перечислено, что нужно от клиента для старта (данные, контакт эксперта)
[ ] 8. Таймлайн расписан по дням с результатом каждого дня
[ ] 9. Метрики успеха измеримы (не "хорошо работает", а ">= 95% точность")
[ ] 10. Дальнейшее движение показывает путь от Discovery к MVP
[ ] 11. Есть ключевая фраза "прототип не выбрасывается, переходит в MVP"
[ ] 12. НЕТ абстракций ("лучшее решение", "современная архитектура")
[ ] 13. Не указаны реальные клиентские имена и компании (если это внешнее предложение)
```

**Если найдена проблема — промпт для исправления:**
```
В предложении Discovery Sprint раздел [X] [размыт / не соответствует сложности /
не привязан к данным клиента]. Перепиши конкретнее: [что нужно].
```

## Deliverables (список артефактов)

Используйте этот чеклист для контроля полноты Discovery Sprint во время его проведения.

### Обязательные артефакты:

- [ ] **Прототип** — развёрнут и доступен по ссылке, клиент может взаимодействовать
- [ ] **Репозиторий** — код на GitHub, структурированный, с README
- [ ] **Отчёт о тестировании** — таблица с результатами: что сработало, что нет, процент точности
- [ ] **Acceptance Criteria** — документ для MVP, по каждому компоненту: что считается "готово"
- [ ] **Смета MVP** — точная стоимость (не вилка), разбивка по этапам, сроки
- [ ] **Архитектурная схема** — как компоненты связаны, какие технологии, где хостится
- [ ] **Data Model** — схема базы данных (SQL или диаграмма)

### Опциональные артефакты:

- [ ] **Метрики точности** — для AI-проектов: precision, recall, accuracy
- [ ] **Нагрузочное тестирование** — если важна производительность
- [ ] **Конкурентный анализ** — если клиент просил сравнить с существующими решениями
- [ ] **Roadmap** — план развития продукта после MVP

## Советы

1. **Цена Discovery Sprint = 30-50% от MVP.** Если MVP стоит 400K — Discovery Sprint за 120-150K логичен
2. **Всегда привязывайте к данным клиента.** "На ваших реальных данных" — ключевая фраза
3. **Прототип должен работать.** Не макет в Figma, а система, куда можно вводить данные
4. **Acceptance Criteria — ваша страховка.** После Discovery Sprint клиент не может сказать "я ожидал другое"
5. **Не перегружайте Discovery Sprint.** Проверяйте 1-2 гипотезы, не весь продукт
6. **Фиксируйте данные от клиента.** Задержка данных = задержка спринта. Пропишите дедлайн
7. **Демо в последний день — обязательно.** Живой показ на реальных данных клиента — это момент, когда продаётся MVP

## Workflow: как создать предложение Discovery Sprint за 20 минут

```
ШАГ 1: Проведите Discovery Call по скрипту 1-05
  ↓ Зафиксируйте контекст: компания, проблема, данные, бюджет, сложность
  
ШАГ 2: Откройте Claude AI (web)
  ↓ Загрузите 3 артефакта:
  • Заметки с Discovery Call (контекст клиента)
  • 1-06-DISCOVERY_SPRINT_TEMPLATE.md (этот справочник)
  • 1-05-DISCOVERY_CALL_SCRIPT.md (для связи скрипта и предложения)
  
ШАГ 3: Промпт:
  "Сгенерируй предложение Discovery Sprint для этого клиента по формату 
   из справочника 1-06. Заполни все 7 разделов: цель, что делаем, deliverables,
   смета, что нужно от клиента, дальнейшее движение, следующий шаг.
   Плюс таймлайн по дням и метрики успеха.
   Сложность проекта: [простой / средний / сложный] — подбери ценовой диапазон."
  
ШАГ 4: Получите результат
  ↓ Claude вернёт предложение на 200-300 строк с TaskFlow-стилем
  
ШАГ 5: Валидация (этот документ)
  ↓ Пройдитесь по чек-листу выше
  
ШАГ 6: Если нужны правки — попросите Claude
  "В разделе [X] [что не так]. Перепиши: [как надо]."
  
ШАГ 7: Отправьте клиенту
  ↓ PDF или в теле письма с кратким сопроводительным текстом
  
ШАГ 8: После согласования — выставите счёт и стартуйте спринт
```

**Итог:** вы не написали предложение Discovery Sprint руками. Вы провели Call, передали контекст Claude, валидировали результат, отправили клиенту. Это и есть роль AI-архитектора на этапе pre-sale.
