# Промпт: Создание демо-версии проекта за 2 часа

> **Тип:** Instruction
> **Модуль:** 8 — Коммерция и ценообразование
> **Для кого:** AI-архитектор, который хочет показать клиенту работающий прототип
> **Цель:** Демо = лучший инструмент продажи. Показать > рассказать.

---

## Философия этого документа

Этот файл — **готовый промпт для Claude Code**. Вы не пишете его сами — копируете и используете.

**Принцип работы:**
- Вы — архитектор и коммуникатор
- Claude Code — исполнитель: читает промпт, собирает демо
- Ваша задача — описать продукт и скопировать правильный промпт

**Workflow:**
```
Вы → копируете промпт → вставляете в Claude Code (VS Code)
       ↓
       прикрепляете контекст (описание проекта + скрин референса)
       ↓
Claude Code → собирает работающее демо за 2 часа
       ↓
Вы → деплоите демо → показываете клиенту → закрываете сделку
```

Промпт уже отлажен. Не нужно его улучшать с первого раза — просто используйте.

---

## Почему демо продаёт лучше КП

| Инструмент | Конверсия | Время на подготовку |
|------------|:---------:|:-------------------:|
| КП (PDF/текст) | 10-20% | 30-60 минут |
| КП + прототип (Figma) | 20-35% | 2-4 часа |
| КП + работающее демо | **40-60%** | **2 часа** |

Клиент может кликать, видеть UI, чувствовать продукт.
Это не скриншот, не макет — это работающий код на реальном URL.

---

## Стратегия: что оставить, что вырезать

### Оставить (показывает ценность)

- Главный экран (дашборд) с моковыми данными
- 1-2 ключевых сценария пользователя (core flow)
- Красивый UI (shadcn/ui + Tailwind)
- Авторизация (хотя бы заглушка)
- Адаптивная вёрстка (мобильный + десктоп)

### Вырезать (тратит время, не продаёт)

- Настоящая авторизация с email-подтверждением
- CRUD всех сущностей (достаточно read + mock)
- Бэкенд-логика (mock data вместо API)
- Платежи и интеграции
- Тестирование и edge cases
- Документация

### Правило 80/20

Демо показывает **20% функций**, которые дают **80% впечатления**.
Клиент должен увидеть результат, а не процесс.

## Деплой демо на Vercel

```bash
# 1. Убедись, что проект собирается
npm run build

# 2. Деплой (если Vercel CLI установлен)
vercel --prod

# 3. Или через GitHub
# Push в репозиторий → Vercel подхватит автоматически
```

### Именование URL

Используй понятный URL для клиента:
- `taskflow-demo.vercel.app`
- `demo-taskflow.vercel.app`

Не: `my-project-abc123.vercel.app`

## Типичные ошибки

### 1. Тратить больше 2 часов
Демо — это инструмент продажи, не начало проекта.
2 часа — потолок. Если не укладываешься — режь скоуп.

### 2. Подключать реальную БД
Mock data. Всегда. Supabase подключишь после предоплаты.

### 3. Показывать пустые состояния
Пустой дашборд не продаёт. Заполни моковыми данными.
Клиент должен видеть «как будет», а не «как может быть».

### 4. Забыть про мобильную версию
Клиент откроет демо на телефоне. Точно. Проверь.

### 5. Не подготовить сценарий показа
Не импровизируй. Пройди по экранам заранее:
Login → Дашборд → Ключевая фича → Второстепенная фича → «Вот так».
3-5 минут. Чётко.
