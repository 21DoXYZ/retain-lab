# 4-27 | HANDOFF.md — Справочник структуры

> Reference-документ: что Claude генерирует для передачи между сессиями.
> Используйте для валидации и формулирования требований — не для ручного заполнения.

> **Тип:** Reference-шаблон передачи между сессиями
> **Когда использовать:** В конце каждой рабочей сессии с Claude Code, если проект продолжится в следующей сессии
> **Результат:** Документ, который следующая сессия Claude Code прочитает и продолжит работу без потери контекста

---

## Философия этого документа

**Вы не пишете HANDOFF.md вручную.** Claude Code сам создаёт его в конце сессии — вы говорите "/handoff" (если настроен скилл) или "создай HANDOFF.md на основе того, что мы сделали сегодня". Claude читает контекст сессии, историю изменений, git-состояние — и генерирует документ.

Зачем тогда этот справочник?

1. **Валидация** — понять, правильно ли Claude заполнил все 9 секций
2. **Корректировка** — если Claude забыл важное архитектурное решение или gotcha, знать как попросить добавить
3. **Коммуникация** — говорить с Claude на языке "добавь gotcha про drag-and-drop в секцию 5" вместо "там не хватает важного"
4. **Контроль качества** — проверить, что следующая сессия сможет продолжить без потери контекста

**Правильный workflow:**
```
Вы → в конце сессии говорите "/handoff" или "создай HANDOFF.md"
Claude → читает контекст сессии, git log, diff, TODO в коде
Claude → генерирует HANDOFF.md со всеми 9 секциями
Вы → используете этот справочник чтобы валидировать результат
Claude → вносит правки (добавляет забытые решения, gotchas)
Вы → коммитите "docs: session handoff" и закрываете сессию
```

В начале следующей сессии — вы говорите "прочитай HANDOFF.md" и Claude загружает весь контекст проекта мгновенно.

---

## Что это такое

Handoff-документ решает главную проблему мультисессионной разработки: **потерю контекста между сессиями**. Claude Code не помнит предыдущие сессии. Без handoff-документа следующая сессия начнёт "с чистого листа" и может:

- Переделать уже сделанную работу
- Нарушить архитектурные решения
- Пропустить известные проблемы
- Не учесть неочевидные зависимости

## Структура HANDOFF.md: 9 секций

Ниже — что Claude должен сгенерировать в каждой секции, как проверить результат и как попросить исправить.

### Секция 1: Статус проекта

**Что Claude генерирует:** текущий этап (scaffold / database / backend / frontend / QA / deploy), процент готовности, последний успешный коммит, текущая ветка.

**Как проверить:** этап соответствует реальности? Процент готовности не оптимистичный? Коммит-хеш верный?

**Промпт для исправления:**
```
В Секции 1 процент готовности завышен — мы сделали только бэкенд,
фронта ещё нет. Пересчитай реалистично.
```

### Секция 2: Что сделано в этой сессии

**Что Claude генерирует:** таблицу задач с колонками "Задача / Статус / Файлы". Статус: завершено / в процессе / заблокировано / не начато.

**Как проверить:** все значимые изменения в сессии попали в таблицу? Статусы честные (не "завершено", если есть незакрытые TODO)?

**Промпт для исправления:**
```
В Секции 2 забыта задача [X] — добавь строку. И поправь статус
задачи [Y] — мы не закончили, там ещё debounce не подключён.
```

### Секция 3: Архитектурные решения

**Что Claude генерирует:** список решений с объяснением "почему именно так" и отметкой "не менять без веской причины".

**Как проверить:** для каждого решения есть причина (не только "что", но и "почему")? Указано ли, что произойдёт при попытке изменить?

**Промпт для исправления:**
```
В Секции 3 не хватает решения про [X] — мы договорились использовать
[Y] вместо [Z] потому что [причина]. Добавь.
```

### Секция 4: Известные проблемы

**Что Claude генерирует:** таблицу "Проблема / Severity / Workaround". Баги, о которых знаем, но не починили. TODO в коде с контекстом.

**Как проверить:** все реальные известные баги указаны? У каждого есть severity и workaround? Нет ли перепутано "не сделано" vs "баг"?

**Промпт для исправления:**
```
В Секции 4 добавь проблему: на мобильном drag-and-drop не работает,
severity Medium, workaround — нужен TouchSensor из @dnd-kit.
```

### Секция 5: Gotchas (подводные камни)

**Что Claude генерирует:** пронумерованный список неочевидных зависимостей с указанием файлов и строк. Вещи, которые "выглядят как баг, но работают правильно".

**Как проверить:** указаны ли конкретные файлы и номера строк? Есть ли объяснение "если убрать X, сломается Y"?

**Промпт для исправления:**
```
В Секции 5 нет gotcha про [X] — в файле [Y] строка [N] есть
неочевидная зависимость. Добавь с объяснением.
```

### Секция 6: Файлы, изменённые в сессии

**Что Claude генерирует:** список файлов из `git diff --name-only` с отметками "новый / изменён". Плюс указание, что добавлено в package.json.

**Как проверить:** список совпадает с реальным git diff? Помечены ли новые файлы vs изменённые?

**Промпт для исправления:**
```
В Секции 6 не хватает файлов — запусти git diff --name-only
и обнови список полностью.
```

### Секция 7: Изменения в базе данных

**Что Claude генерирует:** новые таблицы, столбцы, индексы, RLS-политики. Названия применённых миграций. Seed-данные если добавлялись.

**Как проверить:** указаны ли все миграции из supabase/migrations/? Есть ли ссылка на конкретные файлы миграций? RLS-политики описаны?

**Промпт для исправления:**
```
В Секции 7 пропущена миграция [X] — добавь название и описание
изменений. Также упомяни новую RLS-политику для [таблица].
```

### Секция 8: Переменные окружения

**Что Claude генерирует:** список новых env-переменных, добавленных в сессии. ТОЛЬКО названия и формат — БЕЗ значений.

**Как проверить:** НЕТ реальных значений ключей или токенов? Указан ли формат (URL, API key, boolean)? Если значений быть не должно — но они есть, это угроза безопасности.

**Промпт для исправления:**
```
В Секции 8 УБЕРИ реальные значения переменных — оставь только
названия. Это критично для безопасности.
```

### Секция 9: Следующие шаги

**Что Claude генерирует:** приоритизированный список конкретных задач для следующей сессии. С пометками про зависимости между задачами.

**Как проверить:** задачи конкретные (не "доделать фронт", а "завершить TaskSearch.tsx с debounce 300ms")? Указаны ли зависимости? Есть ли разделение на Приоритет 1 / 2?

**Промпт для исправления:**
```
В Секции 9 задачи слишком абстрактные. Распиши Приоритет 1
конкретнее — какой файл, какую функцию, что именно добавить.
```

## 3. Архитектурные решения

### Drag-and-drop: @dnd-kit вместо react-beautiful-dnd
- **Почему:** react-beautiful-dnd не поддерживается, @dnd-kit активно развивается и лучше работает с React Server Components
- **Не менять:** Переход на другую библиотеку потребует переписать TaskBoard и TaskColumn

### Optimistic updates для статусов
- **Почему:** Перемещение карточки должно быть мгновенным, не ждать ответа сервера
- **Как работает:** useOptimistic в TaskBoard.tsx, откат при ошибке
- **Риск:** Если Supabase не доступен, пользователь увидит откат с задержкой 3-5 секунд

### Фильтры через URL search params
- **Почему:** Фильтры сохраняются при обновлении страницы и можно шарить ссылку
- **Реализация:** useSearchParams + nuqs библиотека

## 4. Известные проблемы

| Проблема | Severity | Workaround |
|----------|----------|------------|
| Drag-and-drop не работает на мобильных | Medium | Touch events не подключены — нужно добавить TouchSensor из @dnd-kit |
| При быстром перетаскивании (2 карточки за 1 сек) возможен race condition | Low | Server Action использует timestamp для ordering, но теоретически может быть коллизия |
| Поиск ищет только по названию, не по описанию | Low | Нужно добавить full-text search через Supabase |

## 5. Gotchas (подводные камни)

1. **TaskBoard.tsx строка 45:** `useMemo` для сортировки задач по колонкам — если убрать, каждый ререндер будет пересоздавать массивы и drag-and-drop сломается (визуальный глюк)

2. **tasks.ts строка 82:** `updateTaskStatus` обновляет ОБА поля: `status` и `updated_at`. Если обновить только `status`, RLS-политика пропустит, но сортировка "последние изменённые" сломается.

3. **TaskFilters.tsx:** Фильтр "Все проекты" передаёт `project_id=all`, не `null`. Серверная функция проверяет именно строку "all" — если поменять на null, фильтр перестанет сбрасываться.
