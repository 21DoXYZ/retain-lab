# 1-08: Talking Points — Справочник структуры

> Reference-документ: что Claude генерирует для подготовки к переговорам с клиентом.
> Используйте для валидации и формулирования требований — не для ручного заполнения.

> **Тип:** Reference-шаблон внутреннего документа
> **Фаза:** Подготовка к переговорам
> **Время применения:** Перед ключевым звонком/встречей с клиентом
> **Результат:** Структурированная стратегия переговоров: аргументы, ответы на возражения, ценовые якоря

---

## Философия этого документа

**Вы не пишете Talking Points вручную.** Claude генерирует их из вашего описания контекста встречи: кто клиент, какой проект обсуждаете, какая цель звонка, что клиент уже знает, где ожидаются возражения.

Зачем тогда этот справочник?

1. **Валидация** — понять, правильно ли Claude попал в тон и аргументы под конкретного клиента
2. **Корректировка** — если тезисы звучат формально или мимо цели, знать как попросить переписать
3. **Коммуникация** — говорить с Claude на языке "усиль аргументацию по срокам, клиент давит на дедлайн" вместо "это не то"
4. **Контроль качества** — проверить, что у вас есть готовая речь для каждого возможного сценария звонка

**Правильный workflow:**
```
Вы → описываете контекст встречи (клиент, проект, цель, известные возражения)
Claude → генерирует готовые Talking Points с тезисами и ответами
Вы → используете этот справочник чтобы валидировать результат
Claude → вносит правки, пока не получится шпаргалка на звонок
Вы → идёте на звонок с документом на втором мониторе
```

---

## Зачем нужен этот документ

Talking Points — это внутренний документ, который ты готовишь перед каждым важным звонком с клиентом. Клиент его НЕ видит. Ты используешь его как шпаргалку во время разговора.

**Проблема, которую решает шаблон:**
- На звонке теряешься, забываешь ключевые аргументы
- Клиент задаёт неожиданный вопрос — не знаешь, как ответить
- Не можешь обосновать стоимость и сроки
- После звонка думаешь «надо было сказать вот это»

**Когда использовать:**
- Перед звонком, на котором обсуждается стоимость проекта
- Перед демонстрацией результатов Discovery Sprint
- Когда клиент просит скидку или сомневается
- Перед встречей с несколькими лицами, принимающими решения
- Когда нужно «продать» переход с одного этапа на следующий

**Когда НЕ использовать:**
- Рутинные статус-апдейты по проекту
- Технические созвоны с командой клиента

---

## Структура документа Talking Points: 5 секций

Документ состоит из 5 секций. Каждая готовит тебя к определённому аспекту переговоров. Ниже — что Claude должен сгенерировать в каждой секции, как проверить и как попросить исправить.

---

### Секция 1: Реалистичный план и сроки

**Что Claude генерирует:** таблицу с понедельной математикой — дата старта, дата дедлайна клиента, разбивка по этапам (Discovery, MVP, калибровка) и вывод — влезает в дедлайн или нет.

**Как проверить:** сроки реалистичные (не «MVP за 2 недели», если там 5 модулей)? Учтены ли этапы Discovery + MVP + калибровка? Есть ли список условий, при которых план работает?

**Промпт для исправления:**
```
В Секции 1 сроки слишком оптимистичные — MVP с AI-компонентами
не делается за 4 недели. Пересчитай по 6-8 недель и покажи
понедельный план.
```

```markdown
## 1. Реалистичный план

### Жёсткая математика

| Период | Недель | Что реально |
|--------|:------:|-------------|
| [ДАТА_СТАРТА] → [ДАТА_ДЕДЛАЙНА_КЛИЕНТА] | [N] недель | Доступное время |
| Этап 0 (Discovery) | [N] недель | Готово к [ДАТА] |
| Этап 1 (MVP) + калибровка | [N] недель | Готово к [ДАТА] |
| Этап 2 (Полный продукт) | [N] недель | Готово к [ДАТА] |
| **Всего (минимум)** | **[N] недель** | **[ВЫВОД: влезает/не влезает в дедлайн]** |

### Понедельный план

| Неделя | Дата | Что происходит |
|:------:|------|---------------|
| 1-2 | [ДАТЫ] | [ОПИСАНИЕ_РАБОТ] |
| 3-4 | [ДАТЫ] | [ОПИСАНИЕ_РАБОТ] |
| ... | ... | ... |

### Условия, при которых план работает

1. [УСЛОВИЕ_1 — данные от клиента к определённой дате]
2. [УСЛОВИЕ_2 — выделенный эксперт]
3. [УСЛОВИЕ_3 — оперативная обратная связь]
4. [УСЛОВИЕ_4 — фиксированный скоуп]
5. [УСЛОВИЕ_5 — нет пауз между этапами]
```

**Зачем:** Когда клиент спрашивает «а можно к лету?» — у тебя есть конкретный ответ с математикой, а не «ну, постараемся».

---

### Секция 2: Что входит в стоимость (скрытая ценность)

**Что Claude генерирует:** список конкретных работ, которые клиент может не осознавать. Плюс список того, что НЕ включено, с объяснением почему.

**Как проверить:** пункты конкретные (не "дизайн", а "проектирование всех экранов, дизайн-система, адаптивная вёрстка")? Упомянуты ли неочевидные работы (документация, обучение команды, тестирование)? Объяснено ли, почему что-то не включено?

**Промпт для исправления:**
```
В Секции 2 пункты слишком общие. Распиши каждый с конкретными
примерами работ — клиент должен увидеть объём.
```

```markdown
## 2. Что входит в стоимость

**[КОМПОНЕНТ — например, Дизайн] включён в стоимость.** В составе работ:

- [ПУНКТ_1 — конкретная работа]
- [ПУНКТ_2]
- [ПУНКТ_3]
- [ПУНКТ_4]
- [ПУНКТ_5]

Что **не включено** (и почему на данном этапе не нужно):
- [ПУНКТ_1 — с объяснением, почему это отдельный проект]
- [ПУНКТ_2]
```

**Зачем:** Когда клиент говорит «а это входит?» — ты уже знаешь ответ. И можешь добавить «кстати, вот это тоже входит» — повышая воспринимаемую ценность.

---

### Секция 3: Тезисы для ответа клиенту

**Что Claude генерирует:** готовые формулировки на типичные вопросы и возражения — по срокам, по стоимости, по скидкам, по подходу, по гарантиям. Каждый тезис — цитата, которую можно произнести дословно.

**Как проверить:** тезисы звучат живо, а не как текст из договора? Есть ли цифры и конкретика вместо "мы профессионалы"? Написаны от первого лица, как прямая речь?

**Промпт для исправления:**
```
В Секции 3 тезисы звучат слишком формально. Перепиши в
разговорном стиле, от первого лица, как будто говорю клиенту
вживую. Добавь конкретные цифры.
```

```markdown
## 3. Тезисы для ответа клиенту

### По срокам

> «[ГОТОВАЯ_ФОРМУЛИРОВКА — что реально, что нет, от чего зависит]»

### По стоимости

> «[ГОТОВАЯ_ФОРМУЛИРОВКА — почему столько, что в рынке, что включено]»

### По скидке

> «[ГОТОВАЯ_ФОРМУЛИРОВКА — почему не можем снизить, какие альтернативы]»

### По нашему подходу / преимуществам

> «[ГОТОВАЯ_ФОРМУЛИРОВКА — Spec-Driven Development, AI-субагенты,
>  почему быстрее и надёжнее классических студий]»

### По гарантиям / рискам

> «[ГОТОВАЯ_ФОРМУЛИРОВКА — Discovery снижает риски, acceptance criteria,
>  фиксированная стоимость после Discovery]»
```

**Формат:** Каждый тезис — цитата, которую можно произнести на звонке дословно. Не заметки, а готовая речь.

---

### Секция 4: Стратегия переговоров

**Что Claude генерирует:** внутренние заметки о тактике — как вести себя, если клиент давит на цену, просит скидку или сомневается. Это не для озвучивания, а для ориентировки.

**Как проверить:** есть ли конкретные тактики ("не снижать цену, а спросить что вырезать из скоупа")? Определены ли варианты оптимизации (что можно вынести в отдельный этап)? Есть ли якорь ценообразования?

**Промпт для исправления:**
```
В Секции 4 тактика размыта. Добавь 3-5 конкретных тактик
на случай давления по цене, с чётким "если клиент говорит X —
отвечаю Y".
```

```markdown
## 4. Стратегия переговоров

**Не давать скидку «просто так».** Вместо этого:

1. [ТАКТИКА_1 — подчеркнуть скрытую ценность]
2. [ТАКТИКА_2 — показать, что цена уже ниже рынка]
3. [ТАКТИКА_3 — если клиент настаивает, спросить: «Что вы
   готовы сократить в скоупе?»]
4. [ВАРИАНТЫ_ОПТИМИЗАЦИИ — что можно вынести в отдельный этап]
5. [ЯКОРЕНИЕ — какую модель ценообразования подсвечивать]
```

---

### Секция 5: Красные линии

**Что Claude генерирует:** список того, что ты НЕ готов обсуждать, и при каких условиях отказываешься от проекта. Это стоп-линии для тебя, клиент их не видит.

**Как проверить:** указана ли минимальная сумма, ниже которой не берёшь проект? Есть ли пункт про предоплату? Указаны ли условия, при которых проект становится нерентабельным?

**Промпт для исправления:**
```
В Секции 5 красные линии слишком мягкие. Добавь жёсткую
минимальную сумму и условие "без предоплаты не стартуем".
```

```markdown
## 5. Красные линии (не озвучивать клиенту)

- Ниже [СУММА] ₽ за этот скоуп — не берём
- Без предоплаты — не работаем
- Если клиент не может выделить эксперта — проект буксует
- Если клиент хочет менять скоуп каждую неделю — фиксируем
  в договоре: изменения = сдвиг сроков + доп. смета
```

---

## Фреймворк ответов на возражения

Универсальные шаблоны для частых возражений, которые Claude использует как базу. Когда ты описываешь конкретного клиента, Claude адаптирует эти формулировки под его контекст и тон.

---

### Возражение: «Дорого»

**Стратегия:** Не спорить о цене, а показать ценность и контекст.

**Вариант 1 — Сравнение с рынком:**
> «Классическая студия разработки берёт за проект такого масштаба [СУММА_ВЫШЕ]. Наша стоимость уже [НА_СКОЛЬКО]% ниже рынка за счёт AI-first подхода, который сокращает время разработки в 2-3 раза. При этом качество не страдает — мы пишем полные спецификации и тестируем каждый компонент.»

**Вариант 2 — Декомпозиция:**
> «Давайте посмотрим на стоимость в разрезе: [СУММА] за [СРОК] недель работы — это команда из [N] специалистов. В пересчёте на человеко-часы это [СТАВКА] ₽/час, что ниже рыночной ставки одного senior-разработчика.»

**Вариант 3 — Сокращение скоупа:**
> «Если стоит задача оптимизировать бюджет — можно обсудить, какие компоненты вынести в следующий этап. Например, [КОМПОНЕНТ] можно реализовать после запуска, когда появятся первые пользователи и реальные данные.»

---

### Возражение: «Долго»

**Стратегия:** Показать математику, предложить параллелирование.

**Формулировка:**
> «Давайте посчитаем вместе. [КОЛИЧЕСТВО] модулей, каждый требует проектирования, разработки, тестирования и интеграции. При параллельной работе — [СРОК] недель. Это агрессивный план, который работает при условии [УСЛОВИЯ]. Если нужно быстрее — можем [ВАРИАНТЫ: сократить скоуп первого этапа / добавить ресурс за доп. стоимость].»

---

### Возражение: «А вы точно справитесь?»

**Стратегия:** Spec-Driven Development как гарантия.

**Формулировка:**
> «Именно для этого существует Discovery Sprint. За [СРОК] и [СУММА] ₽ вы получаете работающий прототип на ваших реальных данных — не обещания, а результат. После Discovery у вас на руках acceptance criteria, точная смета и понимание, можем ли мы технически реализовать то, что вам нужно. Это минимальный риск для вас.»

---

### Возражение: «AI-разработка — это же просто нейросеть генерирует код?»

**Стратегия:** Объяснить разницу между генерацией и архитектурой.

**Формулировка:**
> «Мы не "генерируем сайт через нейросеть". Наш подход — Spec-Driven Development: сначала инженеры пишут детальную спецификацию каждого компонента, потом команда специализированных AI-субагентов работает под управлением наших архитекторов. Database-architect проектирует схему, backend-engineer реализует API, frontend-developer собирает интерфейс, qa-reviewer тестирует. Каждый агент — под контролем человека. Это инженерный процесс, а не генерация.»

---

### Возражение: «У конкурентов дешевле»

**Стратегия:** Спросить, что именно входит в их цену.

**Формулировка:**
> «Важно сравнивать одинаковые вещи. Уточните: в их стоимость входит [ПУНКТ_1], [ПУНКТ_2], [ПУНКТ_3]? Есть ли acceptance criteria? Кто владеет правами на код? Какая гарантия на поддержку? Часто "дешевле" означает, что часть работы не включена или будет доделываться за отдельные деньги.»

---

### Возражение: «Хотим начать без Discovery, сразу MVP»

**Стратегия:** Объяснить риски, но не навязывать.

**Формулировка:**
> «Можем и так. Но в этом случае смета будет с вилкой ±30%, потому что без исследования ваших данных мы не можем гарантировать точные сроки и стоимость. Discovery Sprint стоит [СУММА] ₽ — это [ПРОЦЕНТ]% от стоимости MVP, но он убирает неопределённость и даёт вам работающий прототип. По сути, вы платите [СУММА] ₽ за то, чтобы не рисковать [СУММА_MVP] ₽.»

## Что Claude вернёт для встречи с TaskFlow

Ниже — пример того, что Claude сгенерирует, если вы дадите ему контекст: "Готовлюсь к Zoom-звонку с Иваном Петровым (CEO ООО "Продуктив") по проекту TaskFlow. Он видел предложение Discovery Sprint на 80 тыс, есть сомнения по срокам и цене, хочет к лету MVP". Используйте как образец для сравнения с тем, что получите в своём кейсе.

---

### Контекст встречи

- **Клиент:** Иван Петров, CEO ООО "Продуктив"
- **Проект:** TaskFlow — AI-трекер задач для фрилансеров
- **Формат:** Zoom-звонок, 45 мин
- **Цель звонка:** Согласовать Discovery Sprint, ответить на вопросы о стоимости и подходе
- **Что клиент знает:** Видел предложение Discovery Sprint на 80,000 ₽, хочет обсудить

---

### 1. Реалистичный план

| Период | Недель | Что реально |
|--------|:------:|-------------|
| Апрель --> конец июля | 14 недель | Доступное время |
| Этап 0 (Discovery) | 2 недели | Готово к концу апреля |
| Этап 1 (MVP) | 6 недель | Готово к середине июня |
| Калибровка + запуск | 2 недели | Готово к концу июня |
| **Итого до запуска** | **10 недель** | **Влезает в лето** |

**Ключевой аргумент:** «К концу июня — работающий MVP с AI-планировщиком. Это рабочий продукт, который уже можно показывать первым пользователям и собирать обратную связь.»

---

### 2. Что входит в стоимость

**UI/UX включён.** В составе работ:
- Проектирование всех экранов (дашборд, карточки задач, план дня, настройки)
- Дизайн-система под TaskFlow (цвета, компоненты, типографика)
- Адаптивная вёрстка (десктоп + мобильная версия)
- Дизайн дашбордов аналитики

---

### 3. Тезисы

#### По подходу

> «Наше ключевое направление — AI-first разработка сложных продуктов. Мы не генерируем сайты нейросетью — мы используем Spec-Driven Development: сначала пишем детальную спецификацию каждого компонента, затем команда специализированных AI-субагентов работает под управлением наших инженеров.
>
> Для вашего проекта это означает: database-architect проектирует схему задач и проектов, backend-engineer реализует логику AI-планировщика, frontend-developer собирает интерфейс трекера. Каждый этап — под контролем человека.
>
> Результат: MVP за 6 недель вместо 12-16 в классической студии, при полной прозрачности процесса.»

#### По стоимости Discovery Sprint

> «80 000 рублей за Discovery — это 5% от ориентировочной стоимости всего MVP. За эти деньги вы получаете: работающий прототип AI-планировщика на ваших реальных задачах, отчёт о точности, и фиксированную смету на MVP без вилок. По сути, вы платите 80 тысяч, чтобы не рисковать полутора миллионами.»

#### По срокам

> «Discovery — 2 недели с момента получения ваших данных. MVP — 6 недель после Discovery. К концу июня у вас рабочий продукт. Сроки зависят от двух вещей: скорость передачи данных от вас и доступность для обратной связи по результатам AI.»

---

### 4. Стратегия

1. Подчеркнуть, что UI/UX уже входит — клиент может об этом не знать
2. Если спросит про полную стоимость MVP — дать ориентир 400,000-600,000 ₽, но подчеркнуть: «точную цифру скажем после Discovery, когда поймём сложность AI-классификатора на ваших данных»
3. Если попросит скидку на Discovery — не снижать. 80,000 ₽ — минимальный порог рентабельности для 2-недельного спринта
4. Якорить на Discovery как на страховку: «дешевле проверить гипотезу за 80 тысяч, чем узнать на полпути MVP, что AI не работает с вашими данными»

---

### 5. Красные линии (не озвучивать)

- Ниже 60,000 ₽ за Discovery — не берём
- Без предоплаты 100% — не стартуем
- Если клиент не может дать 50 реальных задач для тестирования — Discovery теряет смысл
- Если хочет «сразу MVP без Discovery» — можем, но смета с вилкой ±40%

## Чек-лист валидации (после генерации)

Когда Claude сгенерировал Talking Points — пройдитесь по этому чек-листу. Если что-то не так, попросите исправить. Плюс — финальная проверка перед самим звонком.

[ ]  7. Секция 3: в каждом тезисе есть цифры / сравнения / конкретика
[ ]  8. Секция 4: стратегия содержит 3-5 конкретных тактик

**Если найдена проблема — промпт для исправления:**

## Workflow: как создать Talking Points за 7 минут

```
ШАГ 1: Подготовьте контекст встречи
  ↓ Соберите: кто клиент (имя, роль, компания), формат встречи,
    цель звонка, что клиент уже знает, ожидаемые возражения,
    дедлайн клиента, бюджет

ШАГ 2: Откройте Claude Code (или Claude web)
  ↓ Подготовьте к загрузке:
    • 1-08-TALKING_POINTS_TEMPLATE.md (этот файл — как reference)
    • Предложение Discovery Sprint, если уже отправлено
    • Ваш контекст встречи

ШАГ 3: Промпт:
  "Сгенерируй Talking Points для звонка с клиентом по reference 1-08.
   Клиент: [имя, роль, компания].
   Проект: [название, краткое описание].
   Формат встречи: [Zoom / офлайн, длительность].
   Цель звонка: [продать Discovery / согласовать MVP / ответить на сомнения].
   Что клиент уже знает: [предложение / стоимость / подход].
   Ожидаемые возражения: [дорого / долго / сомнения в AI].
   Заполни все 5 секций с живыми тезисами."

ШАГ 4: Получите результат
  ↓ Claude вернёт готовую шпаргалку в Markdown

ШАГ 5: Валидация (этот документ)
  ↓ Пройдитесь по 12 пунктам "после генерации"

ШАГ 6: Правки (если нужны)
  ↓ "В Секции [X] тезисы звучат формально — перепиши живее"
    Обычно 1-2 итерации.

ШАГ 7: Прочитайте вслух
  ↓ Это важно: тезисы должны звучать естественно
    в вашем голосе, не как заученный текст

ШАГ 8: На звонок
  ↓ Откройте на втором мониторе, идите на звонок
    Финальные пункты чек-листа (13-17) — прямо перед созвоном
```

**Итог:** вы не пишете Talking Points руками. Вы описали ситуацию, Claude сгенерировал шпаргалку, вы валидировали и проговорили вслух. На звонке — у вас готовая речь под каждое возражение.
