# Batch Data Ingestion

## Обзор

Батч-каналы решают две задачи:

1. **Бэкфилл истории** — разовая загрузка данных за период до включения живого потока
   (моделям нужно минимум 6 месяцев истории).
2. **Регулярная батч-доставка** — если событийного потока нет вовсе, данные могут
   приезжать периодическими дампами или прямым pull из вашей БД.

> Если есть возможность слать события — шлите события
> ([Real-time Event Ingestion](realtime-event-ingestion.md)). Батч — для истории
> и для случаев, когда потока нет.

## Форматы файлов

| Параметр | Значение |
|---|---|
| Формат | **Parquet** (предпочтительно) или CSV |
| Состав | `money_transactions`, `game_transactions`, `game_sessions` за период + **полный свежий снапшот `users`** |
| Схемы полей | [Data Requirements](data-requirements.md) |
| Время | UTC |

## Бэкфилл истории (при подключении)

Живой поток покрывает события **с момента включения (T)**. Историю до T присылайте
дампом — она грузится в аналитические таблицы, на которых обучаются модели.

**Порядок против «дырки» в данных:**

1. Включаем живой поток, фиксируем T.
2. Вы выгружаете дамп за период [конец предыдущей выгрузки → T].
3. Перекрытие в несколько часов не страшно — дубли убираются автоматически.
4. Мы заливаем, валидируем и пересчитываем модели.

**Транзакционные датасеты** — инкрементально (только период), **профили `users`** —
всегда полным снапшотом.

## Регулярные батч-каналы (если потока нет)

| Способ | Кто инициирует | Свежесть | Когда выбирать |
|---|---|---|---|
| Дампы Parquet в object storage (S3/R2) | вы кладёте | часы | классика, минимальная связность систем |
| Прямой pull из read-реплики вашей БД | мы тянем | минуты–часы | если готовы выдать RO-доступ |
| Ручные CSV-выгрузки | вы выгружаете | дни | только на старте/пилоте |

Для object storage согласуются: бакет/префикс, структура путей по датам, расписание,
формат уведомления о готовности партиции. Для pull: адрес реплики, RO-учётка,
allowlist наших IP, watermark-колонки (`updated_at`/`created_at`).

## Требования к загрузке

- **Идемпотентность:** перезаливка данных за любую дату допустима — перед обучением
  берётся последнее состояние каждой записи. Ошиблись в дампе — просто пришлите
  исправленный файл за ту же дату.
- **Rolling window (рекомендация):** ежедневно выгружать данные за последние несколько
  дней с перекрытием — автоматически подхватываются «опоздавшие» транзакции.
- **Валидация на границе:** каждая партия проходит проверки (схема, типы, дубли,
  разрывы дат); расхождения возвращаем отчётом до включения данных в обучение.
- **Маппинг идентификаторов** (если ваш id ≠ `casino_player_id`) выполняется в одном
  месте слоя загрузки — по правилу, согласованному на старте.

## Onboarding: тест → прод

1. **Тестовая загрузка:** небольшой срез данных → проверяем схему, типы, полноту.
   Полнота данных на этом шаге не критична — проверяется техника.
2. **Совместная сверка:** подтверждаем, что данные читаются корректно и сходятся с
   вашими контрольными цифрами (количества, суммы по дням).
3. **Боевая загрузка:** полная история + регулярный инкремент. Модели обучаются
   только на выверенных данных.
