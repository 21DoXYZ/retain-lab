# Data Requirements

## Обзор

Что нужно от оператора, чтобы модели обучились и предсказывали качественно.
Принципы одинаковы для потока событий и батч-загрузки.

## Главные принципы

> **Транзакции лучше агрегатов.** Модели питаются гранулярным поведением (ритм
> депозитов, паттерны ставок внутри дня). Дневные агрегаты теряют сигнал — используйте
> их только если сырые транзакции физически недоступны.

- **Минимум 6 месяцев свежей непрерывной истории.** Не «данные двухлетней давности»:
  модель должна учиться на текущем поведении и текущем трафик-миксе.
- **Тест- и сервис-аккаунты размечены** (`account_type: normal/test/service`) — в
  обучение и скоринг идут только реальные игроки.
- **Статусы денежных операций обязательны** (`completed / rejected / failed / pending`):
  успешные депозиты — сигнал №1 во всех моделях, отклонённые — самостоятельный признак.
- **Единый идентификатор игрока** (`casino_player_id`) во всех датасетах.
- **Время в UTC.** Суточные и «ночные» признаки система сама считает в таймзоне
  оператора (фиксируется на старте интеграции).

## Критичность датасетов

| Датасет | Критичность | Используется |
|---|---|---|
| Депозиты/выводы со статусами (`money_transactions`) | 🔴 критично | все модели; из депозитов восстанавливается VIP-история |
| Профили игроков (`users`) | 🔴 критично | фильтр реальных игроков, FTD, атрибуция, страна |
| Ставки/выигрыши (`game_transactions`) | 🟡 рекомендуется | игровые признаки: ритм, momentum, разнообразие игр |
| Игровые сессии (`game_sessions`) | ⚪ опционально | дашборд и витрины; моделям напрямую не нужны |
| VIP-история | — **не требуется** | выводится детерминированно из депозитов (наше отличие от вендоров) |

## Обязательные поля

### `users` — профиль игрока (1 строка = игрок, upsert)

| Поле | Зачем |
|---|---|
| `casino_player_id` | ключ во всех датасетах |
| `account_type` | `normal` / `test` / `service` — фильтр реальных игроков |
| `reg_date` | лаг регистрация→FTD, стаж |
| `ftd_date`, `ftd_amount` | старт окон LTV/repeat/early-VIP; сумма первого депозита |
| `country` | категориальный признак |
| `affiliate_code`, `affiliate_type` | атрибуция трафика (признак во всех моделях) |

### `money_transactions` — денежные операции

| Поле | Зачем |
|---|---|
| `casino_player_id` | ключ |
| `created_at` (UTC) | окна, гэпы, ритм депозитов |
| `type` | `deposit` / `withdrawal` / `bonus` / `manual_*` / `freespin` |
| `status` | `completed/rejected/failed/pending` — успех фильтруется по статусу |
| `amount` | суммы, лестница депозитов, VIP-уровень |
| `payment_method` | категориальный признак |
| `description` | тип бонуса — признак для рекомендаций офферов |

### `game_transactions` — ставки и выигрыши

| Поле | Зачем |
|---|---|
| `casino_player_id` | ключ |
| `created_at` (UTC) | recency, ритм, ночная доля |
| `transaction_type` | `bet` / `win` / `freespins_bet` / `freespins_win` — разметка фриспинов критична |
| `bet_amount`, `win_amount` | оборот, средняя ставка, чистый результат |
| `game_uuid` | разнообразие игр |
| `aggregator` / `provider` | категориальный признак «основной провайдер» |

## Расширенные данные — функции CRM (второй эшелон)

Моделям эти данные **не требуются** — каждый пункт включает конкретную функцию
продукта. Принцип деградации мягкий: пункта нет → соответствующая функция честно
показывает «нет данных», всё остальное работает.

| Данные | Какую функцию включает |
|---|---|
| `balance_after` в игровых событиях | график и максимум баланса в карточке игрока (аргументы для персонального контакта) |
| События сессий (`session_start` / `session_end`) | «играют сейчас», live-алерты, моментум игрока |
| Справочник игр (`game_uuid` → название) | человекочитаемая аналитика по играм |
| Телефон / email + флаги верификации | звонки и доставка сообщений из CRM (PII-режим согласуется отдельно) |
| Согласия на контакт (opt-in) + события изменения | строгий контроль отправок в автоматических цепочках |
| Стоп-лист (`do_not_contact`) | запрет контакта на уровне системы |
| Поток статусов бонусов (выдан → отыгран / сгорел / отменён) | жизненный цикл бонуса в карточке, бонус-экономика (P&L бонусов) |
| Справочник бонусов (каталог кампаний) | названия/типы бонусов в отчётах и рекомендациях |
| Подтверждение выдачи бонуса (granted / rejected) | замкнутый цикл «оффер → выдача → отклик игрока» |
| IP / User-Agent (сырые, ненормализованные) | антифрод-сигналы, детект мультиаккаунтов |
| Расширенные атрибуты профиля (девайс, канал, статус KYC и т.п.) | дополнительные фильтры конструктора сегментов |
| Callback-эндпоинт + токен на вашей стороне | приём push-сигналов после скоринга ([Predictions Delivery](predictions-delivery.md)) |

Состав второго эшелона согласуется на интеграции — подключать можно поэтапно,
каждый пункт независим от остальных.

## Определение VIP

VIP-критерии оператора фиксируются на старте (метрика, пороги, валюта). Типовая
конфигурация — лестница уровней по накопительным успешным депозитам, например:
Silver ≥ 1 000 · Gold ≥ 25 000 · Platinum ≥ 100 000 · Diamond ≥ 300 000 · Royal ≥ 750 000
(значения — иллюстрация; пороги задаются правилами оператора).
Изменение порогов = переобучение VIP-моделей.

## Качество данных

- **Полнота:** обязательные поля без пропусков; опциональные могут быть null.
- **Консистентность:** суммы в одной валюте/одних единицах (не смешивать основную
  валюту и minor units); один формат времени везде.
- **Дедупликация:** у каждого события/транзакции — стабильный уникальный id; повторная
  отправка того же id безопасна (мы дедуплицируем).
- **Правки задним числом:** перезаливка данных за прошлую дату допустима — перед
  обучением берётся последнее состояние каждой записи.

## Частые вопросы

**В: У нас нет части полей (например, `session_id` или `description`).**
О: Присылайте что есть — обязательный минимум помечен выше. Отсутствие рекомендуемых
полей снижает точность, но не блокирует запуск.

**В: Можно сразу агрегаты по дням?**
О: Можно, но модели потеряют внутридневной сигнал (ритм, ночную долю, «раскачку»
ставок). Согласуйте с нами формат агрегата заранее — и только если транзакции недоступны.

**В: Как с таймзонами?**
О: Шлите UTC. Главное — консистентность: не смешивать таймзоны в одном датасете.
