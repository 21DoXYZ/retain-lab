# Real-time Event Ingestion

## Обзор

Приём событий игроков в реальном времени. Два канала на выбор — **HTTP** (проще) и
**потоковый канал** (для больших объёмов). Оба ведут в один приёмник, формат события одинаковый.
События питают и live-мониторинг, и ML-модели — поэтому важны профиль игрока, статусы
денежных операций и разметка фриспинов.

```
ваш бэкенд ──HTTP POST── ┐
                          ├─►  Sellrise (приём → обработка → модели + дашборд)
ваш бэкенд ──поток───────┘
```

Полная спецификация полей по типам событий (документ для бэкенд-команды оператора)
передаётся на этапе интеграции. Здесь — выжимка.

## Контракт события (v2)

Одно сообщение = одно событие, JSON. Общие поля:

| Поле | Тип | Обяз. | Описание |
|---|---|:--:|---|
| `event_id` | uuid | ✅ | уникальный id — по нему дедупликация; при ретраях шлите тот же |
| `event_type` | string | ✅ | `user` · `bet` · `win` · `session_start` · `session_end` · `deposit` · `withdrawal` · `bonus` |
| `casino_player_id` | int | ✅ | ваш внутренний id игрока |
| `ts` | string | ✅ | UTC, `YYYY-MM-DD HH:MM:SS.mmm` |
| `currency` | string | ⬜ | например `EUR` / `USD` |

Игровые события несут `session_id`, `game_uuid`, `provider`, `bet_amount`/`win_amount`,
`is_freespin`, `balance_after`; денежные — `amount`, **`status`**, `payment_method`,
`is_manual`, `balance_after`; событие `user` — полный профиль (тип аккаунта, даты
регистрации/FTD, атрибуция, балансы) и шлётся при регистрации и изменениях (upsert).

Пример:

```json
{"event_id":"…uuid…","event_type":"deposit","casino_player_id":40,
 "ts":"2026-06-20 16:31:02.001","amount":250.00,"status":"completed",
 "payment_method":"bank_transfer","is_manual":false,"currency":"EUR","balance_after":350.00}
```

> Незнакомые поля можно опускать, но `status` у денежных операций, `is_freespin` у
> игровых и событие `user` критичны для качества прогнозов.

## Канал A — HTTP (рекомендуется для старта)

```
URL:    https://<домен-инсталляции>/ingest/events
Метод:  POST
Заголовки: Authorization: Bearer <INGEST_TOKEN> · Content-Type: application/json
Тело:   одно событие (объект) ИЛИ батч (массив, до 1000)
```

**Ответы:**

| Код | Значение | Что делать |
|---|---|---|
| `200 {"status":"ok","accepted":N}` | принято и записано в буфер | ок |
| `400` | нет обязательных полей / битый JSON | исправить payload, не ретраить как есть |
| `401` | неверный/отсутствующий токен | проверить `Authorization` |
| `413` | батч > 1000 событий | разбить |
| `503` | буфер временно недоступен | **повторить с теми же `event_id`** |

`200` возвращается только после надёжной записи в буфер. Любой не-`200`
(и таймаут/сетевая ошибка) ⇒ ретрай того же запроса.

## Канал B — потоковый канал (Kafka-совместимый)

```
bootstrap.servers:  <выдаётся при подключении>
security.protocol:  SASL_SSL            (TLS публичный, ca-файл не нужен)
sasl.mechanism:     SCRAM-SHA-256
topic:              <выдаётся при подключении>
key:                casino_player_id    (события игрока в одной партиции — порядок сохранён)
value:              JSON события (контракт v2)
```

Рекомендуемые настройки продюсера: `enable.idempotence=true`, `acks=all`.
Референс-реализация продюсера предоставляется по запросу.

## Требования к доставке (оба канала)

1. **`event_id` на каждое событие** — дедупликация включена, дубли безопасны.
2. **At-least-once + ретраи:** лучше дубль, чем потеря.
3. **Outbox/локальный буфер** на вашей стороне: если приём недоступен — копить и
   досылать. Идеал — outbox-запись в той же транзакции, что и бизнес-операция.
4. **`ts` — UTC с миллисекундами.**
5. **Поток:** ключ партиционирования — `casino_player_id`.

## Тестовое подключение

1. Выдаём тестовые доступы (HTTP-токен и/или SASL-логин).
2. Вы шлёте 5–10 фейковых событий по контракту.
3. Мы подтверждаем приём.
4. Включается боевой поток; фиксируется момент T для [бэкфилла истории](batch-data-ingestion.md).

## Чек-лист согласования перед стартом

- Какие из 8 типов событий можете слать? Каких нет?
- Ваш id игрока == `casino_player_id`? Если нет — правило маппинга.
- `status` и `payment_method` у денежных операций — передаёте?
- `is_freespin` и `provider` у игровых — размечаете?
- Суммы: основная валюта или minor units? Сколько знаков?
- Ожидаемый объём: событий/сек в среднем и на пике.
- Исходящие IP (для allowlist), техконтакт, сроки.
