# Authentication & Access

## Обзор

Доступы разделены по принципу наименьших привилегий: у каждого канала — свой механизм
и свой секрет. Компрометация одного токена не открывает остальные каналы.

> 🔐 **Все секреты передаются отдельным безопасным каналом, никогда — в документации,
> тикетах или переписке.**

## Карта доступов

| Канал | Механизм | Секрет | Кто выдаёт |
|---|---|---|---|
| HTTP-приём событий | `Authorization: Bearer <INGEST_TOKEN>` | ingest-токен | мы |
| Потоковый приём событий | SASL_SSL / SCRAM-SHA-256 | SASL-логин + пароль | мы |
| Callback-сигналы (мы → вы) | `Authorization: Bearer <CALLBACK_TOKEN>` | генерируете **вы** для защиты своего эндпоинта | вы |
| Дашборд Sellrise | логин/пароль + роль (RBAC) | учётные записи | мы, по списку сотрудников |

## HTTP-приём событий

Каждый запрос к `POST /ingest/events` — с заголовком:

```
Authorization: Bearer <INGEST_TOKEN>
```

- Токен привязан к оператору; ротация — по запросу, старый токен отзывается.
- `401` — токен отсутствует/неверен: проверьте заголовок, не ретраите запрос как есть.
- Исходящие IP вашего бэкенда добавляются в allowlist (сообщите их до старта).

## Потоковый канал (Kafka-совместимый)

```
security.protocol:  SASL_SSL           (TLS публичный, ca-файл не нужен)
sasl.mechanism:     SCRAM-SHA-256
sasl.username:      <SASL_USER>
sasl.password:      <SASL_PASS>
```

Учётка имеет права только на продюс в выданный топик — ни чтения чужих топиков,
ни администрирования.

## Callback-токен (обратный канал)

Для доставки сигналов мы вызываем **ваш** эндпоинт. Токен для него генерируете вы и
передаёте нам — так вы контролируете и ротацию, и отзыв:

```
POST https://<ваш-домен>/api/sellrise/signals
Authorization: Bearer <SELLRISE_CALLBACK_TOKEN>
```

## Роли дашборда (RBAC)

Доступ к экранам и данным дашборда определяется ролью учётной записи. Матрица создана
под структуру retention-отдела:

| Роль | Доступ |
|---|---|
| `operator` | своя очередь, свои звонки и карточки (без чужих данных) |
| `vip_manager` | свои VIP-игроки и их скоринг |
| `head_department` | данные своего отдела (dept-scope) |
| `head_retention` | весь ретеншен + управление скриптами |
| `analyst` | вся аналитика read-only (без аудио звонков) |
| `director` | управленческая сводка |
| `super_admin` | всё, администрирование |

Принципы: скоуп доступа энфорсит **сервер**, а не интерфейс; PII (телефоны) не
показываются там, где они не нужны для работы; действия аудируются.

## Лучшие практики

- **Разные секреты для разных подсистем.** ETL-контур знает только ingest-токен;
  ваш CRM-приёмник — только callback-токен.
- **Ротация без простоя:** запросите новый токен, переключите трафик, мы отзовём старый.
- **Не логируйте токены** в теле логов и URL — только в заголовках запросов.

## FAQ

**В: Один токен на все операции — можно?**
О: Технически каналов несколько и секреты у них разные by design; «одного токена на всё» не существует.

**В: Что при компрометации?**
О: Сообщите нам — ingest/SASL отзываем немедленно и выдаём новые; callback-токен вы ротируете сами, мы лишь обновляем значение у себя.

**В: Тестовое подключение?**
О: Выдаём тестовые доступы, вы шлёте 5–10 фейковых событий, мы подтверждаем приём — после этого включается боевой поток. См. [Real-time Event Ingestion](realtime-event-ingestion.md).
