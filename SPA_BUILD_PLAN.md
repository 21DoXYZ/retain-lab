## 0. Рамки и принципы (прочитать каждому агенту)

1. **Один SPA на ВСЁ (решение владельца, 15.07).** Итог сборки — полный продукт в одном SPA:
   роли+КЦ+звонилка **И вся аналитика** (обзор, /ggr, когорты, LTV, RFM, аффилиаты, игры, воронки, аудит...).
   **Логика расчётов НЕ переписывается:** Flask (`player_board.py`) становится headless JSON-бэкендом —
   каждый экран получает `/api/*`-эндпоинт, переиспользующий существующие SQL/формулы (одни данные — одни цифры).
   Старые HTML-страницы Flask живут до приёмки паритета (fallback), потом гасим.
2. **Сборка — локально на маке.** Supabase локально (Supabase CLI: `supabase start` — поднимает Docker-стек),
   Next.js — `npm run dev`, Flask — как сейчас (venv, :8050), ClickHouse локальный :8123.
   Деплой на VPS — потом, по готовому гайду `материалы все 2/docker-supabase-guide.md` (те же миграции).
3. **Дизайн = текущая CRM.** Цвета/шрифты/ощущение — ровно как в текущем дашборде.
   Токены обязательны (раздел 4). Никаких новых палитр и шрифтов.
4. **Безопасность = RLS в БД + фильтрация в приложении** (defense-in-depth). Оператор физически
   не может открыть чужого игрока прямым запросом. Секреты Tegsoft живут только на бэкенде (adapter), не в браузере.
5. **Каждое действие пользователя — в `crm.audit_log`** (основа RevShare-прозрачности).
6. **Каждый экран обрабатывает 4 состояния:** loading / empty / error / data (требование ТЗ).
7. **PII не попадает в git** (см. .gitignore); ключи — в `.env`, в git только `.env.example`.
8. Все агенты работают на **Opus 4.8**. QA-агенты волны V — **без права Write** (только читают/тестируют/репортят).

## 1. Ролевая модель — ВСЯ система (не только КЦ)

Роли из ТЗ (жирным) + естественные роли такого продукта (казино-CRM). Enum `crm.user_role` расширяем:

| # | Роль | Кто это | Видит / может |
|---|---|---|---|
| 1 | `super_admin` | мы / владелец платформы | всё + Данные/API, ключи интеграции, создание любых учёток |
| 2 | `director` | **директор / владелец казино (C-level)** | **надзор над ВСЕЙ картиной read-only**: вся аналитика + деньги (GGR/NGR/комиссии) + отчёты отделов + журнал звонков + аудит + audit_log (кто что делал — RevShare-прозрачность); экспорт; НЕ управляет учётками/очередями, НЕ трогает Данные/API |
| 3 | **`head_retention`** | глава ретеншена | всё, кроме системных ключей; распределяет игроков между отделами; создаёт кабинеты аффилиатов; удаляет заметки |
| 4 | **`head_department`** (CC / WA) | глава колл-центра / WhatsApp | игроки своего отдела + выданные; управление операторами своего отдела (создать/заблокировать/передать игроков); журнал звонков отдела; календарь отдела; экспорт |
| 5 | **`operator`** (CC / WA) | оператор | ТОЛЬКО назначенные ему игроки; звонок, заметки (видит все заметки по своим игрокам с авторами), календарь свой; БЕЗ аналитики/денег/экспорта |
| 6 | `vip_manager` | VIP-менеджер | игроки vip_level ≥ порога + назначенные; карточка полная, бонус-история по статусам, звонок, заметки; без денег казино (GGR/NGR) и без Данные/API |
| 7 | `affiliate_manager` | **наш** трафик/аффилиат-менеджер (не путать с внешним аффилиатом) | модуль трафика целиком: /affiliates, карточки аффилиатов, вердикты по источникам, комиссии, выгрузки; заведение кабинетов аффилиатов (по согласованию head_retention); без операционки КЦ |
| 8 | `marketing_manager` | руководитель маркетинга / CRM-менеджер | бонус-экономика (бонусы/эффект/кампании/офферы/игры-сегменты), LTV/сегментация, запуск кампаний (когда появится конструктор); без аудита выводов и без операционки КЦ |
| 9 | `analyst` | аналитик | вся аналитика read-only (обзор, когорты, LTV, RFM, /ggr); БЕЗ контактных PII (телефон/email маскируются), без операционки КЦ; экспорт — по флагу |
| 10 | `finance` | финансист | деньги: /ggr, NGR, комиссии аффилиатов, аудит выводов, сверка с партнёркой; без операционки КЦ, без контактов |
| 11 | `risk_officer` | риск/фрод-офицер | аудит, лента флагов, метки 🎯, Risk/Abuse, записи звонков (прослушивание), карточки без маркетинговых блоков |
| 12 | `support` | саппорт | карточка игрока (сокращённая: бонусы по статусам, макс. баланс за период — п.4.2 ТЗ модулей), заметки; без денег казино и аналитики |
| 13 | **`affiliate`** | внешний аффилиат | ТОЛЬКО игроки своего `affiliate_code`: список, стадии, сигналы модели (остывает/риск/оффер), сокращённая карточка; звонок если есть контакт; свои заметки; БЕЗ денег казино, БЕЗ экспорта, БЕЗ сводных цифр |
| 14 | `viewer` | демо/гость (показ продукта) | read-only, обезличенные данные (блюр PII — режим уже есть в CRM), ничего не пишет |

Принципы матрицы: (а) **данные фильтруются на уровне запросов** (RLS + Flask-проверка JWT), не «спрятанные кнопки»;
(б) ядро этапа 1 — роли **3/4/5/13** (+1 super_admin); роли **2, 6–12, 14 — этап 1.5**: в enum и RLS закладываем сразу,
UI-пресеты доделываем после ядра (для `director` пресет тривиален — read-all, делаем сразу за ядром);
(в) **кто создаёт кого (полная матрица заведения учёток):**
   - `super_admin` (мы) → любые роли, в т.ч. `director`, `finance`, `risk_officer`, `analyst`, `marketing_manager`, `affiliate_manager`, `support`, `viewer` (все НЕ-ретеншн роли — только через нас/директора);
   - `director` → может запросить/подтвердить создание не-ретеншн ролей (заводит super_admin), сам учётки не создаёт (read-only);
   - `head_retention` → ретеншн-вертикаль: `head_department`, `operator`, `vip_manager` + кабинеты `affiliate`;
   - `head_department` → `operator` только своего отдела (создать/заблокировать/сбросить пароль/удалить с передачей игроков);
   - все остальные роли учёток НЕ создают. Каждое создание/блокировка → `audit_log`;
(г) **вертикали:** ретеншн = 3→4→5(+6); казино-функции (2, 7, 8, 9, 10, 11, 12) — параллельные отделы, НЕ ретеншн: пользуются своими срезами дашборда; внешние (13, 14) — изолированы. Руководящие (2, 7, 8, 10) смотрят и решают, операционные (4, 5, 6, 12) работают с игроками.

## 2. Архитектура

```
┌────────────────── SPA (Next.js, порт 3000) — ЕДИНЫЙ UI ──────────────────┐
│ логин·очередь·карточка·звонилка·календарь + ВСЯ аналитика (обзор, ggr,   │
│ когорты, LTV, RFM, аффилиаты, игры, воронки, аудит, монитор, справочники)│
└───────┬──────────────────────────────┬────────────────────────────────────┘
        │ Supabase JS SDK (JWT, RLS)   │ fetch JSON (JWT в заголовке)
        ▼                              ▼
┌─ Supabase self-host ─┐   ┌─ Flask :8050 (существующий) ─┐
│ Auth (GoTrue)        │   │ пакет api/* — ВСЕ данные      │
│ Postgres + RLS       │   │  аналитики для SPA (те же     │
│  схема crm.* (OLTP)  │   │  SQL/формулы, что в HTML)     │
│ Realtime (очереди)   │   │ + Tegsoft ADAPTER (секреты)   │
└──────────────────────┘   │ + Tegsoft WEBHOOK receiver    │
                           └───────────┬───────────────────┘
                                       ▼
                              ClickHouse (аналитика, 62M строк,
                              модели ML — как есть)
Tegsoft Cloud ⇄ (adapter: login/originate/recordings; webhooks → к нам)
```

- **Операционка** (users/assignments/notes/calls/calendar/audit) — Postgres `crm.*`, SPA ходит напрямую (RLS защищает).
- **Аналитика** — только через Flask `/api/*` (проверяет Supabase JWT, фильтрует по роли), ClickHouse наружу не торчит.
- **Звонилка** — только через бэкенд-adapter (сессия Tegsoft на сервере); фиксация звонков: webhook-приёмник пишет в `crm.calls`, оператор добивает исход двумя кликами. Записи — стрим через adapter (см. `tegsoft/TEGSOFT_API_NOTES.md`).
- `crm.player_directory` — лёгкий синк из ClickHouse (id, affiliate_code, vip_level, lifecycle) для RLS и списков; обновляет cron/run_loop.

## 7. Порядок запуска агентов (оркестрация)

- Волны запускаются параллельными Agent-задачами (модель **Opus 4.8** каждому; QA — без Write).
- Каждому агенту в промпт: (1) этот файл, (2) его бриф-раздел, (3) конкретные входные файлы, (4) правило «работай только в своей зоне, чужие файлы не трогай».
- **Свежесть API — обязательна:** перед использованием Next.js / Supabase (supabase-js, GoTrue, RLS-синтаксис) /
  Tailwind / echarts-for-react агент сверяет актуальный синтаксис и версии через **Context7 MCP**
  (`resolve-library-id` → `query-docs`), а НЕ пишет по памяти — версии библиотек быстро меняются.
  Версии пакетов фиксируются в lock-файлах; выбранные мажоры записать в README crm-spa.
- Между волнами — короткая приёмка оркестратором (сборка поднимается, DoD волны выполнен), затем следующая волна.
- Файлы-зоны не пересекаются:
  - A1=`supabase/` · A2=`crm-spa/components`+config · A3=`api/core.py`+blueprint-регистрация · A4=`tegsoft/`
  - B1..B4 = свои папки `crm-spa/app/(app)/<модуль>/`
  - C1..C6 = свои `api/<домен>.py` + `crm-spa/app/(app)/<домен>/` (домены не пересекаются — см. волну 2C)
  - Общий `player_board.py` трогает ТОЛЬКО A3 (добавляет регистрацию blueprint'ов); C-агенты пишут в отдельные `api/*.py`, импортируя готовые helper-функции запросов — сам `player_board.py` не редактируют.
- Итого агентов: волна1 ×4 + волна2 ×4 + волна2C ×6 + волна3 ×5(QA) = **19 запусков** (+оркестратор). Волны 2 и 2C идут одновременно (8 параллельно).
