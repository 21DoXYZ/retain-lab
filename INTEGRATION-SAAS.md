# Revenue Autopilot - подключение данных (гайд для клиента)

Версия 1.0 · для первого тенанта (Hub Content). Домен платформы ниже обозначен
`<DOMAIN>` = **retivo.digital**.

Данные приходят тремя каналами. Для запуска достаточно двух (Stripe + сниппет),
серверный API добавляет точность там, где браузеру верить нельзя.

| Канал | Что даёт | Усилия клиента |
|---|---|---|
| 1. Stripe (ключ + вебхук) | Деньги: подписки, инвойсы, неоплаты, отмены, MRR | 10 минут, без кода |
| 2. Сниппет ra.js | Поведение в браузере: сессии, страницы цен, чекаут, отмена | 1 строка + 1 вызов |
| 3. Server Events API | Продуктовые факты: генерации, расход токенов, low-balance | 1 HTTP-вызов из бэкенда |

Склейка: юзер собирается в одну identity по sha256(email) - Stripe-кастомер,
браузерный посетитель и серверные события сходятся автоматически (правило
≥95% авто-склейки, остаток виден в очереди unmatched).

## 1. Stripe - деньги (10 минут, без кода)

Аккаунт Stripe - ВАШ. Мы не просим доступ к аккаунту: вы сами создаёте ключ
и вебхук и вставляете их в CRM → **Get started → шаг 2**. Ключи хранятся в
пространстве вашего продукта и используются только для ваших данных.

**1a. Restricted key** (только чтение + купоны) - история подписок и скидочные
офферы: Stripe Dashboard → Developers → API keys → Create restricted key:
`Customers: Read · Subscriptions: Read · Invoices: Read · Charges: Read ·
Products/Prices: Read · Coupons: Write`.
Ключ `rk_live_...` вставляется в CRM (проверяем живым запросом к Stripe).
Без него всё считается и рассылается, кроме скидочных офферов - они будут
отклоняться с причиной `stripe_not_configured`.

**1b. Webhook** - для живых событий:
Developers → Webhooks → Add endpoint:

- URL: `https://<DOMAIN>/stripe/webhook/<пространство>` (точный URL с хвостом
  вашего пространства показан в CRM → Get started → шаг 2; без хвоста endpoint
  отвечает 400 - иначе события легли бы не тому клиенту)
- События: `invoice.payment_failed`, `invoice.paid`,
  `customer.subscription.created`, `customer.subscription.updated`,
  `customer.subscription.deleted`, `checkout.session.completed`,
  `checkout.session.expired`, `charge.refunded`
- Signing secret `whsec_...` вставить в CRM → Get started → шаг 2

Подпись проверяется всегда (fail-closed: без секрета endpoint отвечает 400).
Секрет ВАШЕГО вебхука хранится в вашем пространстве - события чужих аккаунтов
подписью не пройдут.
Повторная доставка безопасна: `event_id` детерминирован, дубликаты схлопываются.

**Важно про чекаут**: в Checkout Session передавайте
`client_reference_id = <ваш user_id>` - это мост, который склеивает
Stripe-кастомера с юзером продукта в момент оплаты.

## 1a. Откуда берётся база пользователей (важнее всего)

Сниппет видит только то, что происходит ПОСЛЕ установки. Всё, что было раньше
- вся база регистраций - лежит у вас. Забрать её можно тремя способами, и ни
один не требует писать код:

| Способ | Что даёт | Что нужно от вас |
|---|---|---|
| **Провайдер авторизации** (Supabase, Clerk) | ВСЮ базу, включая бесплатных, и дальше синхронно каждый час | ключ на чтение списка юзеров |
| **Свой админский API** | то же, если у вас своя авторизация | URL списка юзеров + токен |
| **Выгрузка CSV** | всю историю разом (без автообновления) | экспорт таблицы юзеров из админки |
| **Stripe** (уже подключён) | все, кто дошёл до оплаты, с историей | restricted-ключ на чтение |

Колонки в выгрузке называйте как угодно: `User ID`, `uuid`, `E-Mail`, `почта`,
`Registration Date`, `date_joined` - распознаются автоматически. Повторная
загрузка того же файла людей не задваивает.

Что даёт живой сниппет сверх этого: поведение (кто чем пользуется, кто затих,
кто открыл страницу отмены) - именно из него берутся стадии. База отвечает на
вопрос «кто есть», сниппет - «что с ними происходит». Нужны оба.

## 2. Сниппет ra.js - поведение в браузере (1 строка)

Перед `</body>` на всех страницах продукта:

```html
<script src="https://<DOMAIN>/snippet/ra.js"
        data-endpoint="https://<DOMAIN>/ingest/saas/events"
        data-token="<INGEST_TOKEN>"
        data-tenant="<пространство>"></script>
```

`<INGEST_TOKEN>` выдаём мы (регенерируется в CRM: Data/API → Integration keys).
Токен браузерного класса - как ключ аналитики: разрешает только запись событий.

После логина юзера - один вызов:

```js
ra.identify(user.id, user.email);   // email хэшируется ЛОКАЛЬНО (sha256),
                                    // сырой адрес страницу не покидает
```

Дальше сниппет сам шлёт: `session_start` (раз в 30 минут тишины),
`page_view` для страниц /pricing и /cancel, `login` при первом identify.

Произвольные события из фронта:

```js
ra.track("checkout_started");
ra.track("cancel_flow_started");
```

Альтернатива data-атрибутам (SPA): задать `window.RA_CONFIG = {endpoint,
token, tenant}` до подключения скрипта.

## 3. Server Events API - продуктовые факты из бэкенда

Для событий, где источник истины - ваш сервер (расход токенов, статус
генерации). Тот же endpoint, но СВОЙ токен - серверный (выдаётся вместе с ingest-токеном
при создании пространства; секрет бэкенда, в HTML не вставлять). Публичный
сниппет-токен здесь тоже работает, но с ним ingest вырежет открытый email
и пометит source=snippet - для серверных фактов используйте серверный:

```
POST https://<DOMAIN>/ingest/saas/events
Authorization: Bearer <SERVER_EVENTS_TOKEN>
Content-Type: application/json
```

Тело - объект или массив (до 1000 событий за запрос):

```json
{
  "event_id":       "gen-8f2c1a-2026-08-05",
  "tenant_id":      "<пространство>",
  "event_type":     "generation_completed",
  "ts":             "2026-08-05 12:34:56.000",
  "client_user_id": "u_18342",
  "tokens_spent":   12,
  "tokens_balance": 388
}
```

Контракт:
- обязательные поля: `event_id`, `tenant_id`, `event_type`, `ts`;
- идентификация: `client_user_id` (ваш id юзера) - обязательно для серверных
  событий; `email_hash` (sha256 от lower(trim(email))) - если id ещё нет;
- `event_id` уникален на событие: повторная отправка того же id безопасна
  (at-least-once, дубликаты схлопываются) - шлите смело с ретраями;
- `ts` - UTC, `YYYY-MM-DD HH:MM:SS.mmm` (ISO 8601 тоже принимается);
- ответ `200 {"accepted": N}`; `401` - плохой токен; `503` - повторите батч.

### Словарь событий (что шлём и когда)

| event_type | Когда | Доп. поля |
|---|---|---|
| `signup` | регистрация | - |
| `onboarding_step` | шаг онбординга | `meta` |
| `project_created` | создан проект | - |
| `generation_started` | генерация запущена | - |
| `generation_completed` | генерация готова | `tokens_spent`, `tokens_balance` |
| `generation_failed` | генерация упала | - |
| `video_downloaded` / `video_shared` | скачал / пошарил | - |
| `paywall_viewed` | увидел пейволл | `page` |
| `checkout_started` / `checkout_abandoned` | начал / бросил оплату | - |
| `plan_page_viewed` | смотрел страницу плана | `page` |
| `cancel_flow_started` | зашёл в отмену | - |
| `cancel_reason` | причина отмены | `meta` |
| `tokens_low` | баланс < 15% лимита | `tokens_balance` |
| `tokens_exhausted` | токены кончились | - |
| `login` / `session_start` | активность | (сниппет шлёт сам) |

Минимальный полезный набор для старта: `generation_completed` (+ токены),
`tokens_low`, `cancel_flow_started` - на них стоят стадии UPGRADE/SAVE и
кампании K4/K5.

## 4. Что происходит с данными дальше

Событие → шина (Kafka) → ClickHouse → склейка identity (почасово) → стадия
юзера (7 стадий, DUNNING/SAVE/UPGRADE переключаются мгновенно по событию) →
кампании K1-K6 (тик каждые 15 минут) → отчёты Leak audit / Campaign uplift.

Безопасность запуска: платформа стартует в dry-run - ни одно письмо и ни один
оффер не уходит юзерам, пока владелец явно не включит автопилот; первые
14 дней - режим согласования. Каждая кампания несёт 10% контрольную группу:
эффект меряется в долларах инкремента, не «на глаз».

## 5. Чек-лист онбординга

- [ ] Restricted Stripe key передан → мы включаем backfill (история за всё время)
- [ ] Webhook в Stripe создан, `whsec_` передан → живые события идут
- [ ] Сниппет на сайте, `ra.identify` после логина → события в CRM (Home → Setup загорается)
- [ ] `client_reference_id` в Checkout Session → склейка юзер-кастомер
- [ ] Серверные события: минимум `generation_completed` с токенами
- [ ] Учётка клиента в CRM (роль director) → смотрит Leak audit со своими цифрами

## 4a. Адрес почты: хеш из браузера, открытый - с сервера

Сниппет в браузере шлёт ТОЛЬКО `email_hash` (sha256) - сырой адрес не покидает
страницу юзера. Но из хеша адрес не восстановить, поэтому неоплатившему юзеру
(активация, брошенный триал) написать письмо нельзя.

Поэтому Server Events API (серверный, не браузерный) может передать открытый
адрес полем `email` рядом с `email_hash`:

```json
{"event_id":"...","tenant_id":"...","event_type":"signup",
 "ts":"2026-08-05 12:00:00.000","client_user_id":"u_18342",
 "email_hash":"<sha256>","email":"user@example.com","source":"api"}
```

Без него активационные и триальные письма честно отбиваются с причиной
`no_contact` (видно в логе касаний). Юзерам с оплатой адрес и так приходит из
Stripe - там письма работают всегда.

## 4b. Семантика доставки событий

Шлюз отвечает 200 только после подтверждения записи в шину (at-least-once).
При 5xx (например, пересборка шины) СНИППЕТ сам ретраит один раз через 2с;
серверные интеграции должны ретраить 5xx с бэкоффом. Дубликаты безопасны -
event_id дедуплицируется на чтении.

## 5a. Событие ценности (обязательное)

Одно событие продукт ОБЯЗАН слать - момент ценности (юзер получил результат):
Hub Content шлёт `generation_completed`; любой другой продукт - каноническое
`value_moment`. На нём держатся стадия ACTIVATE (дошёл/не дошёл до ценности),
SAVE (пользовался и замолчал) и цель кампании K1.

## 5b. Селф-онбординг кампаний и офферов

Клиент НЕ настраивает цепочки руками: опросник на /onboarding (имя продукта,
юнит ценности, лимиты, триал, потолок скидки, пауза) - и система собирает
каталог офферов и тексты всех кампаний K1-K6 под его продукт (AI-компоновщик
при наличии ключа, иначе детерминированные шаблоны; всё валидируется схемами
и правится потом на /offers и /campaigns). Каркас цепочек - платформенный
(_default для тенантов без пресета), офферы биндятся к шагам по ролям.

## 6. Каналы касаний: как клиент их подключает

Email работает на аккаунте КЛИЕНТА - это наш стандарт. Платформенный аккаунт
остаётся в коде как исключение (см. Б) и включается только по договорённости.

**А. Свой аккаунт Resend (стандарт).** Клиент регистрируется на
resend.com, создаёт API-ключ (Full access) и вставляет его в CRM → Channels →
«Аккаунт отправки». С этого момента письма уходят через ЕГО аккаунт: домен,
репутация, лимиты, статистика и оплата отправки - его. Мы не видим его
переписку и не смешиваем его трафик с чужим. Там же клиент вставляет в Resend
наш URL вебхука доставки (`/public/resend/webhook?tenant=<пространство>`,
показан в CRM) и сохраняет подписной секрет `whsec_...` - по этим событиям
работает список подавления.

**Б. Платформенный аккаунт (исключение).** Ключ не вводится - письма идут
через наш аккаунт Resend, домен клиента создаётся внутри него. Репутация
домена делится с платформой, лимиты и стоимость отправки - наши, поэтому
включаем это только по отдельной договорённости. Для SMS/Viber пока работает
только эта модель.

В обеих моделях КАЖДОЕ КАСАНИЕ УХОДИТ ОТ ИМЕНИ КЛИЕНТА - per-tenant
идентичность отправителя (домен, «от кого», альфа-имя, бот) зашита в платформу.

Всё подключается САМИМ клиентом в CRM → **Channels** (/channel-settings):

**Email** (Resend, аккаунт клиента):
0. Зарегистрироваться на resend.com, в разделе API Keys создать ключ с правом
   Full access и вставить его в «Ваш аккаунт Resend» (проверяем живым запросом
   к Resend). Без ключа канал не запускается: домен создавать негде.

1. Клиент вводит поддомен отправки (`mail.клиент.com`) - мы создаём домен
   в нашем Resend и показываем DNS-записи (DKIM/SPF/MX) таблицей с копированием.
2. Клиент добавляет записи в свой DNS и жмёт «Check DNS» - статус станет
   verified (минуты-часы на распространение DNS).
3. Клиент задаёт «От кого»: имя + адрес строго на подключённом поддомене.
   Канал активен; адреса юзеров уже есть из Stripe-склейки. Прогрев ведём мы.
   (Если ключ Resend ещё не введён - запрос сохраняется со статусом
   awaiting_provider и досоздаётся автоматически при первом Check.)

**Доставляемость и закон (работает само, менять нечего):**
- в каждом письме - ссылка отписки с подписью (HMAC) и заголовки
  `List-Unsubscribe` + `List-Unsubscribe-Post` (одноклик у Gmail/Outlook);
- отписка, жалоба на спам и жёсткий баунс кладут адрес в список подавления
  НАВСЕГДА; раннер проверяет список перед каждым касанием и пишет в лог
  `rejected / suppressed`;
- письмо уходит в двух частях (HTML + текст), id письма от Resend пишется в
  лог отправки - по нему вебхуки доставки находят конкретное касание.

**SMS / Viber** (DecisionTelecom, наш аккаунт):
1. Клиент вводит желаемое альфа-имя (латиница/цифры, до 11 знаков).
2. Мы регистрируем имя на его бренд через менеджера DT (1-3 рабочих дня);
   заявка видна как pending_approval, активация = перенос `requested_*` ->
   `*_sender` в tenants.json (делает платформа).

**Telegram** (бот клиента - партнёрство не нужно):
1. Клиент в @BotFather создаёт бота с именем/аватаром своего продукта
   (`/newbot`, затем `/setuserpic` и `/setdescription` - юзеры видят именно их).
2. Вставляет токен в CRM - мы валидируем его (getMe) и вешаем вебхук
   `https://<домен>/ingest/saas/tg/<tenant>` с секретом (fail-closed 403).
3. Юзеров подключает диплинком `https://t.me/<бот>?start=<client_user_id>`.
   БЕЗ id в ссылке чат не с кем связать: юзер, нашедший бота поиском, создаст
   контакт без привязки к аккаунту продукта. Два способа выдать ссылку:

   **а) кнопка в продукте (рекомендуется)** - любой элемент с атрибутом
   `data-ra-telegram`; сниппет сам подставит ссылку с id текущего юзера и
   спрячет элемент, если канал не подключён:

   ```html
   <a data-ra-telegram>Получать уведомления в Telegram</a>
   ```

   Программно доступно `ra.telegramLink()` -> строка или `""` (канал выключен).
   Клик по такому элементу шлёт событие `telegram_connect_clicked` - по нему
   видно, сколько людей вообще жмут кнопку против тех, кто дошёл до Start.

   **б) ссылка руками** - для писем и серверных шаблонов: подставить свой
   `client_user_id` (тот же, что уходит в `ra.identify`).

4. Нажатие Start прилетает вебхуком и превращается в contact_update с
   consent=true (привязка по payload). `/stop` или блокировка бота -> отзыв
   согласия (юзер восстанавливается по chat_id).

Где брать подписчиков: лучше всего работает предложение в МОМЕНТ ЦЕННОСТИ
(сразу после результата), хуже всего - переключатель в настройках аккаунта.
Покрытие видно на карточке канала («подключено с согласием: N»).

**WhatsApp**: единственный канал, где нужен онбординг бизнеса клиента у Meta
(WABA) - ведём через DecisionTelecom, включаем по запросу.

**Остальные каналы** - клиент передаёт контакт с согласием тем же Events API:

```json
{
  "event_id":       "contact-u18342-viber",
  "tenant_id":      "<пространство>",
  "event_type":     "contact_update",
  "ts":             "2026-08-05 12:00:00.000",
  "client_user_id": "u_18342",
  "meta":           "{\"channel\":\"viber\",\"address\":\"380631112233\",\"consent\":true}"
}
```

- `channel`: `sms` | `viber` | `whatsapp` | `telegram`;
- `address`: номер в международном формате без «+» (или chat_id для telegram);
- `consent`: true только при явном согласии юзера на этот канал (дата и текст
  согласия храните у себя); отзыв согласия = то же событие с `consent: false`.

Правила отправки (зашиты в раннер, статусы видны в логе касаний):

| Ситуация | Что делаем | Статус в логе |
|---|---|---|
| нет контакта в канале | не отправляем | `rejected / no_contact` |
| контакт без согласия | не отправляем | `rejected / no_consent` |
| адрес в списке подавления (баунс, жалоба, отписка) | не отправляем никогда | `rejected / suppressed` |
| номер +1 (США) в SMS | не отправляем (TCPA: иски $500-1500 за сообщение) | `rejected / us_sms_blocked` |
| телефон не разбирается (мусор в поле) | не отправляем, прогон остальных продолжается | `rejected / invalid_phone` |
| провайдер ответил 5xx/429 или оборвалась сеть | повторяем на следующем тике, до 3 раз | `retry` |
| после 3 неудачных повторов | сдаёмся и идём дальше по цепочке | `rejected / http_5xx` |
| контроль (holdout) | молчим намеренно | строки нет |

Телефоны нормализуются автоматически: `+38 (063) 111-22-33` и `380631112233` -
один и тот же контакт. Касанием в отчётах считается только то, что реально
ушло (`sent`/`queued`/`issued`, плюс `dry_run` в безопасном режиме) - отбитые
попытки и отложенные повторы в цифру касаний не попадают.

Кампания сама выбирает канал шага; фолбэка «нет телеграма - шлём почтой» в v1
нет: шаг привязан к своему каналу.

**Где смотреть**: CRM → Data/API → Channels - статус ключей каждого провайдера
и покрытие базы контактами/согласиями по каналам.

**Рекомендация по набору контактов** (из плейбука): предлагать Telegram-бота
«видео готово» + бонус-токены за подключение - верифицированный канал в один
тап; WhatsApp с OTP для гео, где Telegram слаб.
