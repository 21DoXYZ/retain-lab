# Replenishment Autopilot v1 (спека, драфт 2026-08-26)

Ставка №1 из JTBD-ресёрча e-commerce ЮВА: предиктивный реордер расходников
через WhatsApp с оплатой ссылкой или COD в один тап. В ЮВА эту работу не
закрывает никто (OMS кончаются на исполнении заказа, WhatsApp-CRM не знают
покупок, Klaviyo не умеет WhatsApp). Валидация модели: Chewy Autoship - 83%
выручки. Прототип механики уже в проде у SimbaGo (carestatus, «корм
заканчивается»): эта спека обобщает его с кормов на любые расходники и
переносит на платформенный уровень Revenue Autopilot.

## Принципы (унаследованы от carestatus, проверены в бою)

1. **Не гадать.** План потребления создаётся только при явной привязке
   «клиент × SKU» (подтверждённый заказ отслеживаемого SKU). Нет привязки -
   нет плана и нет пуша.
2. **Учиться только на подтверждённых циклах.** EWMA-базлайн скорости
   потребления обновляется только когда клиент подтвердил «закончилось»
   (реордер или явный ответ), продления «ещё есть» в обучение не идут.
3. **Пуш, который раздражает, хуже отсутствующего.** Жёсткие частотные
   лимиты на уровне движка, не промпта: не чаще 1 напоминания в 7 дней на
   SKU-план, не больше 2 в неделю на клиента; тихие часы тенанта; дневной
   бюджет канала (личный номер - 20/день).
4. **Read-only поверх источников.** Слой производный: единственные живые
   сущности - план цикла и базлайн; остальное кэш и лог.

## Модель данных (ClickHouse, retention.*)

```
replenishment_plans          -- один купленный «пакет» расходника
  tenant_id, plan_id, identity_id, sku, order_ref,
  status ACTIVE|QUEUED|FINISHED,
  started_at, predicted_days, extension_days,
  finished_at, finish_reason USER_CONFIRMED|REORDERED|EXPIRED|CANCELLED
  (Replacing по plan_id)

consumption_baselines        -- скорость потребления пары
  tenant_id, identity_id, sku, baseline_days, last_cycle_days,
  cycles_count  (Replacing по (tenant, identity, sku))

replenishment_sku_attrs      -- что делает SKU отслеживаемым
  tenant_id, sku, eligible, pack_size, unit, default_days
  (дефолт цикла до первого обучения; заполняется мерчантом в CRM
   или LLM-бэкфиллом по названию товара - как backfill_food_attributes
   у SimbaGo, MANUAL не перезаписывается)
```

Сигналы/пуши идут существующим контуром кампаний: новый событийный триггер
`replenishment_due` (сегодня ≤ started + predicted + extension - lead_days)
встаёт рядом с T1/T2/T3; касание - через send_whatsapp (личный WAHA →
Cloud API фолбэк → email), лог в campaign_send_log, holdout и uplift -
штатные.

## Источники покупок (что создаёт план)

1. **Собственный чекаут тенанта** - серверное событие `order_confirmed`
   (Server Events API, с открытым email/phone) с items[{sku, qty}].
2. **Синк заказов маркетплейсов** (Shopee/TikTok/Tokopedia) - отдельная
   спека MARKETPLACE-ORDERS-SYNC; даёт sku+дату, но контакт появляется
   только после капчи (QR-вкладыш).
3. **Read-only экспорт / коннектор базы** - бэкфилл истории заказов при
   онбординге: сразу тёплая база планов, предиктор не ждёт первого цикла.

Правило создания: заказ подтверждён/оплачен -> для каждого eligible SKU
в заказе создать план ACTIVE (или QUEUED, если активный цикл той же пары
ещё идёт). predicted_days = baseline пары, иначе медиана по SKU у тенанта,
иначе default_days из атрибутов. Дубль-защита по (plan, order_ref).

## Флоу реордера (то, чего нет ни у кого)

Сообщение в WhatsApp в день `due - lead_days`:

  «Судя по прошлой покупке, {product} заканчивается. Продлить?»
  [Заказать снова] [Ещё есть] [Больше не напоминать]

- **[Заказать снова]** - подписанная ссылка (HMAC, аналог unsubscribe) на
  предзаполненный чекаут тенанта: тот же SKU, тот же адрес, выбор
  оплата-ссылкой (Xendit/карта) или COD. Один тап + подтверждение.
  Для маркетплейс-капчи без своего чекаута - fallback: диалоговый реордер
  оператором из WA-инбокса.
- **[Ещё есть]** - +N дней к циклу (extension), не учится.
- **[Больше не напоминать]** - eligible=off для пары, согласие не трогаем.
- Реордер закрывает цикл REORDERED и открывает новый план; USER_CONFIRMED
  (явное «кончилось») - единственное, что двигает EWMA.

Ответы приходят в существующий вебхук личного WAHA / Cloud API; парсинг
кнопок - по payload шаблона (Cloud) или по тексту-коду (личный номер).

## Конфиг тенанта (tenants.json)

```
replenishment: {
  enabled: false,          # рубильник, деф. выкл
  lead_days: 4,            # за сколько дней до конца напоминать
  channel_ladder: ["whatsapp", "email"],
  quiet_hours: наследуются из tenants.timezone,
  max_per_customer_week: 2
}
```

Автопилот тенанта и SIGNALS_DRY_RUN действуют как везде (двойной рубильник).

## Экономика касания

Реордер-напоминание - utility-класс Meta (~Rp357+VAT в Индонезии), окупается
с одного чека при среднем чеке от ~Rp50k. Личный номер (WAHA) - бесплатно,
но бюджет 20/день и бан-риск: для масштаба тенант переезжает на Cloud API
(шаблоны версионируются как в wa_templates.py).

## KPI v1

- % планов, закрытых REORDERED (цель: >20% к 3-му циклу; Chewy-норма недостижима сразу).
- Uplift выручки против holdout (штатный uplift_report, goal = order_confirmed/14d).
- Жалобы/отписки канала < 0.5% получателей.

## Раскатка

1. SimbaGo - первый тенант и референс: carestatus остаётся владельцем
   WhatsApp-пушей у SimbaGo (не дублировать!); платформа в v1 берёт email
   и in-app для SimbaGo, а WhatsApp-реордер обкатывает на втором тенанте
   ЛИБО SimbaGo мигрирует пуши на платформу целиком (решение владельца).
2. Второй тенант - бренд расходников (beauty/supplements/кофе) с Shopee +
   WhatsApp-админом: полный контур капча -> предикция -> реордер.
