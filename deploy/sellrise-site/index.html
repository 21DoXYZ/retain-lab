Варианты интеграции

Вариант A — HTTP push (рекомендуется для старта). Ваш бэкенд шлёт события на наш эндпоинт. Минимум инфраструктуры с вашей стороны: HTTP-клиент + ретраи + outbox.

Вариант B — потоковый канал (Kafka-совместимый API). Продюс напрямую в потоковый приёмник (SASL_SSL). Для больших объёмов и когда у вас уже есть событийная шина.

Вариант C — batch pull/дампы. Если событийного потока нет: регулярные Parquet-дампы в object storage или прямой pull из read-реплики вашей БД. Детали — Batch Data Ingestion.

Итоговый поток


Ваша платформа → Аутентификация → Поток событий (+бэкфилл) → ML-скоринг →
→ Предсказания → Дашборд / Сигналы / Выгрузки → Действия retention-команды →
→ Реакция игрока возвращается событиями → цикл замыкается

Частота пересчёта: предсказания обновляются ежедневно (ночной скоринг); переобучение моделей — еженедельно.

Ключевое отличие от скоринг-вендоров: предсказания приходят не «сырыми скорами в API», а внутри готовой операционки — с назначениями, звонками, статусами и обратной связью по каждому контакту. Слой действий уже построен.

Authentication & Access

Обзор

Доступы разделены по принципу наименьших привилегий: у каждого канала — свой механизм и свой секрет. Компрометация одного токена не открывает остальные каналы.

🔐 Все секреты передаются отдельным безопасным каналом, никогда — в документации, тикетах или переписке.

HTTP-приём событий

Каждый запрос к POST /ingest/events — с заголовком:


Authorization: Bearer <INGEST_TOKEN>
  • Токен привязан к оператору; ротация — по запросу, старый токен отзывается.
  • 401 — токен отсутствует/неверен: проверьте заголовок, не ретраите запрос как есть.
  • Исходящие IP вашего бэкенда добавляются в allowlist (сообщите их до старта).

Потоковый канал (Kafka-совместимый)


security.protocol:  SASL_SSL           (TLS публичный, ca-файл не нужен)
sasl.mechanism:     SCRAM-SHA-256
sasl.username:      <SASL_USER>
sasl.password:      <SASL_PASS>

Учётка имеет права только на продюс в выданный топик — ни чтения чужих топиков, ни администрирования.

Callback-токен (обратный канал)

Для доставки сигналов мы вызываем ваш эндпоинт. Токен для него генерируете вы и передаёте нам — так вы контролируете и ротацию, и отзыв:


POST https://<ваш-домен>/api/sellrise/signals
Authorization: Bearer <SELLRISE_CALLBACK_TOKEN>

Роли дашборда (RBAC)

Доступ к экранам и данным дашборда определяется ролью учётной записи. Матрица создана под структуру retention-отдела:

РольДоступ
operatorсвоя очередь, свои звонки и карточки (без чужих данных)
vip_managerсвои VIP-игроки и их скоринг
head_departmentданные своего отдела (dept-scope)
head_retentionвесь ретеншен + управление скриптами
analystвся аналитика read-only (без аудио звонков)
directorуправленческая сводка
super_adminвсё, администрирование

Принципы: скоуп доступа энфорсит сервер, а не интерфейс; PII (телефоны) не показываются там, где они не нужны для работы; действия аудируются.

Лучшие практики

  • Разные секреты для разных подсистем. ETL-контур знает только ingest-токен;

ваш CRM-приёмник — только callback-токен.

  • Ротация без простоя: запросите новый токен, переключите трафик, мы отзовём старый.
  • Не логируйте токены в теле логов и URL — только в заголовках запросов.

FAQ

В: Один токен на все операции — можно? О: Технически каналов несколько и секреты у них разные by design; «одного токена на всё» не существует.

В: Что при компрометации? О: Сообщите нам — ingest/SASL отзываем немедленно и выдаём новые; callback-токен вы ротируете сами, мы лишь обновляем значение у себя.

В: Тестовое подключение? О: Выдаём тестовые доступы, вы шлёте 5–10 фейковых событий, мы подтверждаем приём — после этого включается боевой поток. См. Real-time Event Ingestion.

Data Requirements

Обзор

Что нужно от оператора, чтобы модели обучились и предсказывали качественно. Принципы одинаковы для потока событий и батч-загрузки.

Главные принципы

Транзакции лучше агрегатов. Модели питаются гранулярным поведением (ритм депозитов, паттерны ставок внутри дня). Дневные агрегаты теряют сигнал — используйте их только если сырые транзакции физически недоступны.
  • Минимум 6 месяцев свежей непрерывной истории. Не «данные двухлетней давности»:

модель должна учиться на текущем поведении и текущем трафик-миксе.

  • Тест- и сервис-аккаунты размечены (account_type: normal/test/service) — в

обучение и скоринг идут только реальные игроки.

  • Статусы денежных операций обязательны (completed / rejected / failed / pending):

успешные депозиты — сигнал №1 во всех моделях, отклонённые — самостоятельный признак.

  • Единый идентификатор игрока (casino_player_id) во всех датасетах.
  • Время в UTC. Суточные и «ночные» признаки система сама считает в таймзоне

оператора (фиксируется на старте интеграции).

Определение VIP

VIP-критерии оператора фиксируются на старте (метрика, пороги, валюта). Типовая конфигурация — лестница уровней по накопительным успешным депозитам, например: Silver ≥ 1 000 · Gold ≥ 25 000 · Platinum ≥ 100 000 · Diamond ≥ 300 000 · Royal ≥ 750 000 (значения — иллюстрация; пороги задаются правилами оператора). Изменение порогов = переобучение VIP-моделей.

Качество данных

  • Полнота: обязательные поля без пропусков; опциональные могут быть null.
  • Консистентность: суммы в одной валюте/одних единицах (не смешивать основную

валюту и minor units); один формат времени везде.

  • Дедупликация: у каждого события/транзакции — стабильный уникальный id; повторная

отправка того же id безопасна (мы дедуплицируем).

  • Правки задним числом: перезаливка данных за прошлую дату допустима — перед

обучением берётся последнее состояние каждой записи.

Частые вопросы

В: У нас нет части полей (например, session_id или description). О: Присылайте что есть — обязательный минимум помечен выше. Отсутствие рекомендуемых полей снижает точность, но не блокирует запуск.

В: Можно сразу агрегаты по дням? О: Можно, но модели потеряют внутридневной сигнал (ритм, ночную долю, «раскачку» ставок). Согласуйте с нами формат агрегата заранее — и только если транзакции недоступны.

В: Как с таймзонами? О: Шлите UTC. Главное — консистентность: не смешивать таймзоны в одном датасете.

Real-time Event Ingestion

Обзор

Приём событий игроков в реальном времени. Два канала на выбор — HTTP (проще) и потоковый канал (для больших объёмов). Оба ведут в один приёмник, формат события одинаковый. События питают и live-мониторинг, и ML-модели — поэтому важны профиль игрока, статусы денежных операций и разметка фриспинов.


ваш бэкенд ──HTTP POST── ┐
                          ├─►  Sellrise (приём → обработка → модели + дашборд)
ваш бэкенд ──поток───────┘

Полная спецификация полей по типам событий (документ для бэкенд-команды оператора) передаётся на этапе интеграции. Здесь — выжимка.

Контракт события (v2)

Одно сообщение = одно событие, JSON. Общие поля:

ПолеТипОбяз.Описание
event_iduuid✅уникальный id — по нему дедупликация; при ретраях шлите тот же
event_typestring✅user · bet · win · session_start · session_end · deposit · withdrawal · bonus
casino_player_idint✅ваш внутренний id игрока
tsstring✅UTC, YYYY-MM-DD HH:MM:SS.mmm
currencystring⬜например EUR / USD

Игровые события несут session_id, game_uuid, provider, bet_amount/win_amount, is_freespin, balance_after; денежные — amount, status, payment_method, is_manual, balance_after; событие user — полный профиль (тип аккаунта, даты регистрации/FTD, атрибуция, балансы) и шлётся при регистрации и изменениях (upsert).

Пример:


{"event_id":"…uuid…","event_type":"deposit","casino_player_id":40,
 "ts":"2026-06-20 16:31:02.001","amount":250.00,"status":"completed",
 "payment_method":"bank_transfer","is_manual":false,"currency":"EUR","balance_after":350.00}
Незнакомые поля можно опускать, но status у денежных операций, is_freespin у игровых и событие user критичны для качества прогнозов.

Канал A — HTTP (рекомендуется для старта)


URL:    https://<домен-инсталляции>/ingest/events
Метод:  POST
Заголовки: Authorization: Bearer <INGEST_TOKEN> · Content-Type: application/json
Тело:   одно событие (объект) ИЛИ батч (массив, до 1000)

Ответы:

КодЗначениеЧто делать
200 {"status":"ok","accepted":N}принято и записано в буферок
400нет обязательных полей / битый JSONисправить payload, не ретраить как есть
401неверный/отсутствующий токенпроверить Authorization

200 возвращается только после надёжной записи в буфер. Любой не-200 (и таймаут/сетевая ошибка) ⇒ ретрай того же запроса.

Канал B — потоковый канал (Kafka-совместимый)


bootstrap.servers:  <выдаётся при подключении>
security.protocol:  SASL_SSL            (TLS публичный, ca-файл не нужен)
sasl.mechanism:     SCRAM-SHA-256
topic:              <выдаётся при подключении>
key:                casino_player_id    (события игрока в одной партиции — порядок сохранён)
value:              JSON события (контракт v2)

Рекомендуемые настройки продюсера: enable.idempotence=true, acks=all. Референс-реализация продюсера предоставляется по запросу.

Требования к доставке (оба канала)

  1. event_id на каждое событие — дедупликация включена, дубли безопасны.
  2. At-least-once + ретраи: лучше дубль, чем потеря.
  3. Outbox/локальный буфер на вашей стороне: если приём недоступен — копить и

досылать. Идеал — outbox-запись в той же транзакции, что и бизнес-операция.

  1. ts — UTC с миллисекундами.
  2. Поток: ключ партиционирования — casino_player_id.

Тестовое подключение

  1. Выдаём тестовые доступы (HTTP-токен и/или SASL-логин).
  2. Вы шлёте 5–10 фейковых событий по контракту.
  3. Мы подтверждаем приём.
  4. Включается боевой поток; фиксируется момент T для бэкфилла истории.

Batch Data Ingestion

Обзор

Батч-каналы решают две задачи:

  1. Бэкфилл истории — разовая загрузка данных за период до включения живого потока

(моделям нужно минимум 6 месяцев истории).

  1. Регулярная батч-доставка — если событийного потока нет вовсе, данные могут

приезжать периодическими дампами или прямым pull из вашей БД.

Если есть возможность слать события — шлите события (Real-time Event Ingestion). Батч — для истории и для случаев, когда потока нет.

Бэкфилл истории (при подключении)

Живой поток покрывает события с момента включения (T). Историю до T присылайте дампом — она грузится в аналитические таблицы, на которых обучаются модели.

Порядок против «дырки» в данных:

  1. Включаем живой поток, фиксируем T.
  2. Вы выгружаете дамп за период [конец предыдущей выгрузки → T].
  3. Перекрытие в несколько часов не страшно — дубли убираются автоматически.
  4. Мы заливаем, валидируем и пересчитываем модели.

Транзакционные датасеты — инкрементально (только период), профили users — всегда полным снапшотом.

Требования к загрузке

  • Идемпотентность: перезаливка данных за любую дату допустима — перед обучением

берётся последнее состояние каждой записи. Ошиблись в дампе — просто пришлите исправленный файл за ту же дату.

  • Rolling window (рекомендация): ежедневно выгружать данные за последние несколько

дней с перекрытием — автоматически подхватываются «опоздавшие» транзакции.

  • Валидация на границе: каждая партия проходит проверки (схема, типы, дубли,

разрывы дат); расхождения возвращаем отчётом до включения данных в обучение.

  • Маппинг идентификаторов (если ваш id ≠ casino_player_id) выполняется в одном

месте слоя загрузки — по правилу, согласованному на старте.

Onboarding: тест → прод

  1. Тестовая загрузка: небольшой срез данных → проверяем схему, типы, полноту.

Полнота данных на этом шаге не критична — проверяется техника.

  1. Совместная сверка: подтверждаем, что данные читаются корректно и сходятся с

вашими контрольными цифрами (количества, суммы по дням).

  1. Боевая загрузка: полная история + регулярный инкремент. Модели обучаются

только на выверенных данных.

Витрины предсказаний

Каждая модель ежедневно перезаписывает свою витрину скоров. Ключ везде — casino_player_id. Полный справочник витрин и колонок (состав предиктивного слоя) передаётся отдельным документом на этапе интеграции.

Канал 1 — дашборд Sellrise

Скоры выведены туда, где принимается решение:

  • Карточка игрока — вся история + прогнозы (LTV-полоса, риск, next-best-action).
  • Пул / Пульт / Играют сейчас — очереди работы с назначением оператору в один клик.
  • Моя очередь — задачи оператора; исход звонка двигает статус, реакция игрока

(депозит/игра ≤7 дней) фиксируется автоматически.

  • /ltv, /actions — ранжирование базы по ценности и списки действий.

Доступ — по ролям (Authentication & Access). VIP-скоры в карточке и сигналах — ближайший релиз (витрины уже наполняются).

Канал 3 — выгрузки колл-центру

Ежедневные сегментные списки со скорами, приоритетом и рекомендацией: at-risk · dormant · churned · never-deposited. XLSX, выгружаются из дашборда; состав колонок настраивается под скрипты колл-центра.

Мониторинг и статус моделей

  • Свежесть: дашборд показывает cutoff данных; scored_at/model_version приходят

в каждом батче сигналов.

  • Здоровье скоринга: сервисный GET /health возвращает время и тайминги

последнего прогона; повторный запуск скоринга защищён от параллельного выполнения.

  • Качество моделей: метрики фиксируются в реестре при каждом переобучении

(еженедельный цикл); деградация видна по сравнению версий.
