# Перенос: личный WhatsApp через QR (WAHA) в другой проект

Инструкция для разработчика. Здесь описано, как фича устроена в этом
репозитории (21DoXYZ/retain-lab, приватный - попросите владельца добавить
ваш GitHub-аккаунт в collaborators), какие файлы взять и как перенести её
в другой стек. Всё, что нужно скопировать, лежит в этом репо - пути точные.

## Что это за фича (глазами пользователя)

1. Владелец на экране каналов жмёт «Подключить личный WhatsApp», подтверждает
   риск (неофициальный протокол, номер могут забанить - это фиксируется).
2. На экране появляется QR. Он сканирует его телефоном, как WhatsApp Web.
3. Статус становится WORKING, номер подтянулся. Входящие сообщения падают
   в инбокс CRM (список чатов + переписка), оператор отвечает из карточки.
4. Автокасания по умолчанию ВЫКЛЮЧЕНЫ. Владелец может включить их вторым
   явным тумблером - тогда кампании пишут в WhatsApp первым (email как
   запасной), но только привязанным контактам с согласием и не больше
   дневного бюджета номера (деф. 20/день). Массовой рассылки с личного
   номера не бывает физически - это защита от бана, а не пожелание.

## Архитектура (5 частей)

```
[телефон владельца] --QR--> [WAHA container] --webhook+HMAC--> [backend]
                                                                  |
[CRM UI: QR-поллинг, инбокс, ответ] <--REST--> [backend] --> [БД wa_messages]
```

1. **WAHA** - готовый контейнер `devlikeapro/waha` (движок NOWEB, free-версия
   держит ОДНУ сессию на инстанс). Порт наружу не публикуется: backend ходит
   к нему по внутренней docker-сети, вебхук WAHA бьёт в backend тоже по
   внутренней сети.
2. **Модуль-клиент WAHA** - вся работа с его API в одном файле.
3. **REST-эндпоинты** - старт сессии / QR+статус / отключение / инбокс / ответ.
4. **Вебхук-приёмник** - статусы сессии и входящие/исходящие сообщения,
   подпись HMAC-sha512 сырого тела (заголовок `X-Webhook-Hmac`).
5. **UI** - карточка канала с QR-поллингом + экран инбокса.

## Файлы, которые копировать (в порядке переноса)

### 1. Инфраструктура - docker-compose

`docker-compose.vps.yml`, сервис `waha` (строки ~76-85):

```yaml
waha:
  image: devlikeapro/waha:latest
  environment:
    WHATSAPP_API_KEY: ${WAHA_API_KEY:-}     # свой секрет, любая строка
    WHATSAPP_DEFAULT_ENGINE: NOWEB          # без Chromium, лёгкий движок
  volumes:
    - waha_sessions:/app/.sessions          # сессия переживает рестарт
    - waha_media:/app/.media
  restart: unless-stopped
  # порт наружу НЕ публиковать: backend ходит по внутренней сети
```

Тома `waha_sessions`, `waha_media` добавить в volumes. Backend-сервису дать
env: `WAHA_URL=http://waha:3000`, `WAHA_API_KEY=<тот же секрет>`,
`BOARD_INTERNAL_URL=http://<имя backend-сервиса>:<порт>` (адрес, куда WAHA
будет бить вебхуком по внутренней сети).

### 2. Ядро - клиент WAHA

**`stripe_sync/wa_personal.py` (324 строки) - копируется целиком**, это
самодостаточный модуль на stdlib (urllib, hmac), без внешних зависимостей.
Что внутри:

- `session_name(tenant)` - имя сессии `tenant_<id>` (задел под мульти-сессию
  в WAHA Plus; в free-версии сессия одна).
- `start_session(tenant)` - POST /api/sessions в WAHA: создаёт сессию с
  NOWEB-store (без него WAHA не отдаёт историю чатов!) и вебхуком на
  `BOARD_INTERNAL_URL/<путь вебхука>` с HMAC-ключом.
- `get_status(tenant)` -> (ok, status, number). Статусы WAHA:
  STARTING -> SCAN_QR_CODE -> WORKING; FAILED = сессия упала.
- `get_qr_png(tenant)` - PNG QR-кода (base64 наружу), только в статусе
  SCAN_QR_CODE.
- `drop_session(tenant)` - удалить сессию (отключение).
- `verify_webhook(tenant, body, header)` - проверка HMAC-sha512 СЫРОГО тела.
- `webhook_hmac_key(tenant)` - ключ выводится из серверного секрета
  (`UNSUB_SECRET` у нас; в вашем проекте возьмите любой постоянный серверный
  секрет и передайте параметром).
- `send_text(tenant, chat_id, text)` - ручной ответ оператора.
- `list_lids(tenant)` - разгадка LID->телефон (WhatsApp прячет номера за
  `@lid`-идентификаторами; без этого в инбоксе бессмысленные id вместо
  номеров).

Единственная связь с нашим проектом - импорт `UNSUB_SECRET` (строки 30-33).
Замените на свой конфиг-секрет.

### 3. REST-эндпоинты подключения

`api/saas.py`, блок «WhatsApp: ЛИЧНЫЙ номер через QR» (строки ~2290-2455):

- `POST /saas/channels/whatsapp/personal` - старт. ТРЕБУЕТ `accept_risk: true`
  в теле, иначе 400: без явного «понимаю, что номер могут забанить» не
  включаем. Время согласия пишется в конфиг тенанта.
- `GET /saas/channels/whatsapp/personal/qr` - статус + QR (PNG base64).
  Фронт поллит его раз в ~2с, пока не WORKING.
  **КРИТИЧЕСКАЯ ЛОВУШКА (выучена на проде): никакого авто-оживления упавшей
  сессии из этого поллинга.** В момент скана движок на секунды перезапускает
  сокет, статус мелькает FAILED - если поллинг «оживляет» сессию, он убивает
  почти завершённую привязку (Intentional Logout ровно в момент скана).
  Рестарт - только явной кнопкой.
- `POST /saas/channels/whatsapp/personal/disconnect` - отключение.
- `GET /saas/wa/chats` - список чатов (агрегат по `wa_messages` + разгадка
  LID + привязка чата к юзеру продукта через контакты).
- `GET /saas/wa/messages?chat=` - переписка одного чата.
- `POST /saas/wa/reply` - ручной ответ (единственный путь отправки).
- `POST /saas/wa/start-chat` - написать первым по номеру.

Эндпоинты - тонкие обёртки над `wa_personal.py`, переносятся почти дословно
в любой фреймворк. Замените наши `require_auth`/`_tenant_arg_write` на вашу
авторизацию, `ca.update_tenant` - на ваше хранилище настроек тенанта.

### 4. Вебхук-приёмник

`api/public.py`, маршрут `POST /wa/personal/<tenant>`, функция
`wa_personal_webhook` (строки ~426-480):

- маршрут БЕЗ авторизации пользователя, но с проверкой `X-Webhook-Hmac`
  (fail-closed: не сошлось - 403);
- событие `session.status` -> обновить статус/номер тенанта в конфиге;
- событие `message` (оба направления!) -> строка в таблицу `wa_messages`;
- входящее с нашим подписанным кодом из connect-ссылки -> привязка
  client_user_id + событие согласия (см. `stripe_sync/wa_templates.py`,
  `connect_url()` - подписанная ссылка wa.me; если в вашем проекте привязка
  к юзеру не нужна, этот кусок можно опустить).

ВАЖНО: вебхук слушается на ВНУТРЕННЕМ адресе compose-сети. Наружу его
публиковать не нужно (и не надо).

### 5. Хранилище

`saas_schema.sql`, таблица `retention.wa_messages` (строки ~901-912):

```sql
CREATE TABLE IF NOT EXISTS wa_messages (
    tenant_id   LowCardinality(String),
    chat_id     String,
    wa_msg_id   String,
    direction   LowCardinality(String),   -- in | out
    text        String,
    sender_name String,
    ts          DateTime64(3)
) ENGINE = ReplacingMergeTree(ts)
ORDER BY (tenant_id, chat_id, wa_msg_id);
```

Это ClickHouse; в Postgres - обычная таблица с UNIQUE(tenant_id, chat_id,
wa_msg_id) и upsert'ом (Replacing = дедуп повторных доставок вебхука).
Плюс три поля в конфиге тенанта: `wa_personal_status`, `wa_personal_number`,
`wa_personal_risk_accepted`.

### 6. UI (если нужен наш)

- `crm-spa/components/saas/ChannelsView.tsx` - карточка канала: кнопка с
  подтверждением риска, QR-картинка, поллинг статуса до WORKING, кнопка
  Disconnect. Ищите по «whatsapp/personal».
- `crm-spa/components/saas/WaInboxView.tsx` - инбокс: чаты слева, переписка
  справа, поле ответа, «написать первым».

Если в целевом проекте другой фронт - UI-контракт простой: поллинг
`GET .../qr` каждые 2с, рисовать `qr_png` (base64), при `WORKING` показать
номер; инбокс = два GET + два POST из п.3.

### 7. Тесты

`stripe_sync/tests/test_whatsapp.py` - подпись вебхука, статусы, маппинг
сообщений. Переносятся вместе с модулем.

## Порядок работ (чек-лист)

1. Поднять WAHA-контейнер (compose из п.1), секрет `WAHA_API_KEY` в env.
2. Скопировать `wa_personal.py`, заменить импорт секрета на свой.
3. Создать таблицу `wa_messages` + 3 поля конфига тенанта.
4. Повесить вебхук-приёмник (п.4) на внутренний адрес, прописать
   `BOARD_INTERNAL_URL` так, чтобы WAHA до него доставал.
5. Добавить 7 REST-эндпоинтов (п.3) под вашу авторизацию.
6. UI: кнопка с accept_risk -> QR-поллинг -> инбокс.
7. Проверка живьём: старт -> QR на экране -> скан телефоном -> WORKING +
   номер -> отправить сообщение НА этот номер с другого телефона -> оно в
   инбоксе -> ответить из CRM -> пришло на телефон.

## Инварианты, которые НЕЛЬЗЯ потерять при переносе

1. **accept_risk обязателен** - это неофициальный протокол против ToS Meta,
   банят личный номер клиента. Согласие с таймстампом в конфиге.
2. **Авторассылки - только за вторым явным тумблером и с дневным бюджетом.**
   В базовой поставке канал ручной. Если переносите и автокасания (у нас:
   wa_personal_automation + wa_personal_daily_cap, деф. 20/день, WhatsApp
   первым в лестнице с фолбэком в email) - бюджет и отдельное согласие
   владельца обязательны: без них личный номер клиента забанят за неделю.
3. **Вебхук - только с проверкой HMAC сырого тела**, fail-closed.
4. **Не оживлять сессию из QR-поллинга** (ловушка Intentional Logout, п.3).
5. **WAHA free = одна сессия.** Второй клиент = второй инстанс WAHA или
   WAHA Plus. Имя сессии уже tenant-скоупное - код готов.
