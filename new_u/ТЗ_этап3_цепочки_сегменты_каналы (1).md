# ТЗ Этап 3: Конструктор сегментов · Конструктор цепочек · Каналы доставки

_Дата: 07.07.2026. Продолжение `ТЗ_CRM_перестройка_на_модули.md` (этапы 1–2 — перегруппировка меню). Основа: `Цепочки_Василий_разбор.md` (блоки, 4 ML-точки, каталог цепочек), `для ЦРМ.xlsx` (фильтры сегментов), `Maestra_референс_для_Retivo.md` (что брать из архитектуры), ТЗ Bonus Analytics (события бонусов)._

**Что строим:** три связанных компонента внутри модуля «Retention-автоматизация», которые превращают систему из «умного советчика» в исполнителя:

```
СЕГМЕНТ (кто)  →  ЦЕПОЧКА (что и когда делать)  →  КАНАЛ (как доставить)
        и на каждом шаге — ML: тайминг · бонус · A/B · критик
```

**Дизайн не меняем** — всё в текущем стиле CRM, из существующих компонентов (правило из ТЗ этапов 1–2, п.4.1: состояния loading/empty/error/data обязательны для каждого нового экрана).

**Главная развилка всего этапа (решить ДО разработки):** система не хранит PII (контактов). Отправка сообщений возможна в двух режимах — см. п.4.3. Режим для пилота выбрать с Соломоном/Андреем.

## 1. Компонент «Конструктор сегментов»

### 1.1 Принцип
Сегменты создаёт **оператор (клиент), не мы** — ключевое требование Василия: «свои сегменты мы делать не можем, их делает компания — нужно дать им возможность их создавать». Наши преднастроенные сегменты (8 бонус-кампаний, архетипы, RFM) остаются как шаблоны-примеры, которые можно клонировать и править.

### 1.2 Структура фильтра
- Условие = **поле + оператор + значение**. Операторы по типу поля: числа (=, ≠, >, <, между, в топ-N%), даты (до/после/между, относительные: «больше N дней назад», «в ближайшие N часов»), enum (входит в список / не входит), флаг (да/нет/не заполнено).
- Условия объединяются в **группы И / ИЛИ с вложенностью** (минимум 2 уровня — как «группы ИЛИ» на скринах Maestra).
- **Исключающие сегменты**: «НЕ входит в сегмент X» (пример из реальной цепочки Olymp: «НЕ в сегменте "Безопасность ограничение"»).
- Live-счётчик размера сегмента при редактировании («сейчас подходит N игроков»).
- У сегмента: имя, системное имя (латиницей, как `casinoTRG2depARS5093Startbonusa` у Olymp), описание, автор, дата.
- Экспорт списка игроков сегмента в CSV/XLSX (механизм уже есть на `/`).

### 1.3 Пересчёт
- **По расписанию** — по умолчанию раз в сутки, время настраивается (у Olymp — 10:00). Показывать «последний пересчёт N ч назад».
- **Real-time вход** — опция «игрок попадает в сегмент немедленно по событию» (депозит, ставка, логин из live-потока). Нужна для триггеров цепочек; считать только для сегментов, помеченных как триггерные (экономия ресурсов).

### 1.4 Каталог полей — источник истины: `для ЦРМ.xlsx` (158 фильтров, 15 разделов)
Файл Василия покрывает каталог полностью — реализовывать по нему. Состав разделов:

| № | Раздел | Фильтров | Примечания для реализации |
|---|---|---|---|
| 0 | Даты событий (универсальный фильтр) | 4 | базовый механизм «событие X было/не было за период N раз» — фундамент всего конструктора, делать первым |
| 1 | Профиль игрока | 23 | всё из таблицы users; «Бренд/лицензия» — после мультибренда |

> Важно: Василий сам включил в каталог send-time-оптимизацию, next-best-bonus, контрольную группу и A/B-группу (п.128–129, 140–143 файла) — то есть требования каталога и наши 4 ML-точки сходятся 1-в-1.

**Зависимости по данным (сводно):** разделы 0–6, 9, 10 + логины — считаются из текущих данных, блокеров нет. Раздел 8 — нужны бонус-события; раздел 11 — события доставки; разделы 7, 12 (частично), 13, 14 — новые события от казино (добавить в спецификацию API по мере надобности).

## 2. Компонент «Конструктор цепочек»

### 2.1 Блоки (полный набор — из реальной системы Olymp/Maestra)
| Блок | Что делает | Обязательные настройки |
|---|---|---|
| **Триггер** | запускает цепочку | тип (см. 2.2) + сегмент/событие |
| **Действие** | делает что-то | начислить бонус · отправить сообщение · тег · в очередь Пульта · произвольный вебхук |
| **Условие по клиенту** | развилка ДА/НЕТ по полям игрока | любое поле из каталога п.1.4 |
| **Условие по ответу вебхука** | развилка по ответу внешней системы | «бонус начислен успешно?» |
| **Ожидание** | пауза | фиксированное · динамическое (от события) · **ML-персональное** (точка №1) · окно часов (11:00–22:00, по таймзоне игрока) |
| **Сплит** | делит поток | доли % или по сегменту |
| **A/B-тест** | сравнение веток | N вариантов + контрольная группа |
| **Лимит** | ограничение объёма | не больше N в час/день |
| **Стоп / Цель** | завершение | целевое событие + окно атрибуции |

### 2.2 Триггеры
1. **Попал в сегмент** (основной способ — 90% цепочек).
2. **Событие real-time** из live-потока: депозит, отказ депозита, ставка, логин, открыл кассу и не оплатил, крупный проигрыш в сессии, конец сессии.
3. **По расписанию** (ежедневно, по дате, годовщина).

Анти-дубль: игрок не может войти в одну цепочку повторно, пока не вышел (настройка: разрешить повтор через N дней).

### 2.3 Действия
- **Начислить бонус** — вебхук-команда в казино (`bonus_grant`), ответ обрабатывается блоком «условие по вебхуку». Бонус: фиксированный из справочника ИЛИ **ML-рекомендованный** (точка №2 — поле уже есть в `/signals`).
- **Отправить сообщение** — канал конкретный или **каскад** (п.4.2), шаблон + язык.
- **Поставить тег / снять тег** на игрока.
- **Передать в очередь Пульта** — задача менеджеру (для VIP: «не бонусом, а человеком» — из каталога цепочек).
- **Произвольный вебхук** — POST на URL клиента.

### 2.4 Обязательные проверки перед каждой отправкой (системные, не блоки)
Opt-in канала ✓ · канал существует у игрока ✓ · языковая версия шаблона есть ✓ · **не находится в игровой сессии прямо сейчас** (live-поток; настройка «ждать конца сессии») · лимит частоты коммуникаций (fatigue: не больше N сообщений за M дней, глобальная настройка + переопределение в цепочке) · не в сегменте «Безопасность/ограничения».

### 2.5 Жизненный цикл цепочки
Статусы: draft → active → paused → archived. **Версионирование** (v1.0, v2.0 — как у Olymp): изменение активной цепочки создаёт новую версию, игроки внутри доходят по старой. Копирование цепочки. Многоуровневый поиск по списку (требование Василия: «умный поиск», у Olymp 250 сценариев).

### 2.6 Аналитика по шагам (закрывает боль Василия — «ручные выгрузки»)
На каждом блоке: вошло / прошло / выпало (и почему: не прошёл условие, нет канала, opt-out, лимит). По цепочке: конверсия в цель, по веткам A/B, деньги (депозиты игроков после прохождения, стоимость выданных бонусов, стоимость отправок). Экран «узкие места» — шаги с максимальным отсевом.

### 2.7 Цель и контрольная группа
- Цель цепочки = настраиваемое событие (депозит №N, любой депозит, ставка, логин) + окно атрибуции (по умолчанию 14 дней).
- **Контрольная группа обязательна по умолчанию** (16%, редактируется) — без неё эффект не доказуем. Отчёт: конверсия веток vs контроль + денежный эффект.

### 2.8 Четыре ML-точки (killer-фичи, из разбора Василия)
1. **ML-ожидание.** Блок «Ожидание» в режиме «персонально»: модель считает момент по медиане перехода похожих игроков (метод оплаты, сумма, паттерн). Пример-эталон: BLIK $15 → медиана 2-го депозита 28 мин → касание на ~32-й минуте, если не внёс. База уже есть: `expected_gap` в формулах системы. Fallback: если данных мало — фиксированное время.
2. **ML-бонус.** В действии «начислить бонус» опция «рекомендованный моделью» (+ прозрачность: почему — «любимая игра X, средний чек Y»).
3. **A/B: ML vs человек vs контроль.** Пресет сплита 42/42/16: ветку A ведёт ML (тайминг+бонус), ветку B — настройки менеджера, контроль — тишина. Отчёт «насколько ML лучше человека» — главный аргумент продаж.
4. **ML-критик.** Фоновый анализ активных цепочек: сравнивает настройки (время ожидания, бонус, сегмент) с фактическим поведением игроков. Замечания с объяснением: «ожидание 24 ч, медиана возврата сегмента 55 мин — теряете игроков», «бонус фриспины, но 41% сегмента — спортбеттеры». В списке цепочек — иконка ⚠️, клик — список замечаний, кнопка «применить» (создаёт новую версию с правкой).

### 2.9 Сегмент кампании и «повторить для отреагировавших» (фича Optimove — запрос Василия 13.07)
Каждая запущенная кампания/цепочка автоматически порождает **сегменты по реакции**: получили · открыли · кликнули · сделали целевое действие. Кнопка **«Повторить кампанию для отреагировавших»**: даже если кампания в целом не окупилась (пример Василия: 10 000 отправок за $5k, вернулась сотня на $3k), отреагировавшая сотня — готовый сегмент для повтора через заданный промежуток. Система при этом уже знает: какая коммуникация, какой бонус, когда и как сработали на этих игроках.

### 2.10 Двусторонняя интеграция статусов касаний (обязательное требование)
Принцип: система должна видеть не только «кому выдали бонус», но и **все касания и их исходы** — иначе аналитика слепа по всем, кого коснулись без бонуса. Источники: события доставки (п.4.5) + статусы колл-центра из ТЗ по ролям/звонилке (звонок: дозвон/недозвон/неверный номер; SMS отправлен). Опыт Василия (PinUp): статус звонка обязан возвращаться в систему, чтобы ретен не слал SMS на несуществующие номера — «оператор слышит, живой ли номер, а ретен нет». Выгрузки в Excel допустимы только как временный режим — целевая интеграция по API в обе стороны.

### 2.11 Библиотека шаблонов (пресеты при старте)
Из каталога стандартных цепочек (логика 10 лет не меняется — меняются оффер и тайминг): Welcome/онбординг → FTD · 1-й→2-й депозит (эталон — разобранная цепочка ARS 5093) · Лесенка депозитов 2→10 · Failed deposit recovery (динамическое ожидание от «открыл кассу») · Winback/реактивация (нарастающие офферы) · Anti-churn (по падающему паттерну + churn-скору) · VIP-цепочка (через очередь Пульта, человеком) · Cashback-триггеры (мгновенный/недельный по VIP-тиру) · Реферал. Каждый пресет = клонируемый черновик с пустыми офферами.

## 4. Компонент «Каналы доставки»

### 4.1 Набор каналов
MVP (фаза 3а): **вебхук-команда в казино** (казино отправляет само — см. режимы ниже) · **email** (SMTP клиента или наш) · **Telegram-бот**. Фаза 3в: WhatsApp / Viber / SMS через агрегатор (Twilio/Infobip) · web/mobile push · авто-прозвон. (Каталог каналов — из разбора Василия: email → авто-прозвон → мессенджеры → SMS.)

### 4.2 Каскад
Порядок каналов настраивается на уровне цепочки (по умолчанию: от дешёвого к дорогому). Логика: канал 1 → нет доставки/открытия за N часов → канал 2 → … Стоимость отправки по каналам задаётся в настройках — участвует в аналитике денег (п.2.6).

### 4.3 Два режима работы с PII (⚠️ решение до разработки)
- **Proxy-режим (рекомендуемый для старта, соответствует позиции Соломона «PII не храним»):** мы не знаем контактов. Команда `send_message {player_id, channel, template_id, params}` уходит вебхуком в казино, казино отправляет само и возвращает статус. Плюс: безопасность = наш козырь. Минус: нужна доработка на стороне казино.
- **Direct-режим:** клиент передаёт контакты, мы шлём сами (SMTP/боты/агрегатор). Контакты — в отдельном шифрованном хранилище, доступ только у сервиса отправки, в UI не показываются (маскирование). Требует пересмотра фразы «PII не хранится» в футере и плана security-аудита.

### 4.4 Шаблоны сообщений
Редактор шаблонов: текст + переменные подстановки ({name опционально, {bonus_amount}, {game}, {link}) · **мультиязычность** (версии шаблона по языкам; блок «условие: языковая версия» из цепочки Olymp становится автоматикой: язык берётся из профиля) · превью · для email — простой HTML в текущем стиле.

### 4.5 События доставки (обратная связь)
`sent / delivered / opened / clicked / failed / opt_out` по каждой отправке → в аналитику шагов, в fatigue-счётчик, в раздел 8 фильтров. Без них каскад «нет открытия за N часов → следующий канал» не работает.

## 5. Новые события и команды API (дополнение к спецификации)

**Команды к казино (исходящие):**
```
bonus_grant     {player_id, bonus_id | ml_recommended, params}   → ответ: granted / rejected + причина
send_message    {player_id, channel, template_id, params}        → только proxy-режим
player_tag      {player_id, tag, set|unset}
```

**События от казино (входящие, добавить к текущему /ingest/events):**
```
касса:   cashier_opened, deposit_failed (+причина)               → триггеры failed-deposit цепочки
бонусы:  bonus_claimed, bonus_activated, wagering_progress,
         wagering_completed, bonus_converted, bonus_expired      → из ТЗ Bonus Analytics (уже согласовано)
согласия: opt_in_changed {channel, granted}                      → актуальность согласий
доставка: message_status {sent|delivered|opened|clicked|failed}  → proxy-режим
звонки:  call_status {reached|no_answer|busy|invalid_number, outcome} → от колл-центра/звонилки (п.2.10)
```

## 6. Definition of Done (чек-лист приёмки фазы 3а)

```
[ ] Оператор сам создаёт сегмент из полей каталога (И/ИЛИ, вложенность, исключение сегментов), видит live-счётчик
[ ] ML-поля доступны в конструкторе как обычные фильтры
[ ] Пресет «1-й → 2-й депозит» запускается на сегменте и проходит путь:
    триггер → бонус-вебхук → проверка ответа → проверки → отправка (email/TG/proxy) → ожидание → проверка цели
```
