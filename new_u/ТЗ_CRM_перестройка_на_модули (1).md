# ТЗ: перестройка CRM (cas.21do.xyz) на модульную структуру

_Дата: 07.07.2026. Основание: разборы звонков (Сергей/1x, Василий), конкурентный анализ (MICO, Maestra/Smartico), ТЗ по Bonus Analytics от CRM-специалиста._

**Главный принцип:** режем продукт не «по типам экранов», а **по сценариям использования** — каждый модуль = одна боль + один пользователь (кресло) + одно управленческое действие. Существующие экраны НЕ удаляются и НЕ переписываются — они перегруппировываются в модули; новая функциональность помечена отдельно.

**⚠️ Дизайн НЕ меняем.** Визуально всё остаётся ровно как в текущей CRM: тот же тёмный сайдбар, те же цвета, шрифты, карточки, таблицы, стили строк и бейджей. Это ТЗ — только про **структуру меню, группировку экранов и новые блоки данных**, собранные из уже существующих UI-компонентов системы. Файл `Retivo_модули_демо.html` (в этой же папке) использовать ТОЛЬКО как схему «что где лежит и какие блоки на экране» — его визуальный стиль НЕ переносить.

## 2. Целевая структура меню (to-be): 7 модулей

Новый сайдбар. Порядок групп фиксированный — он же логика продаж (вход → расширение → ядро):

```
[ВХОД]
  📡 Трафик и аффилиаты
  🐋 VIP-радар
[РАСШИРЕНИЕ]
  🎁 Бонус-экономика
  🛡 Риск и фрод
[ЯДРО]
  ⚡ Retention-автоматизация
[СЛОЙ / ФУНДАМЕНТ]
  📊 Аналитика
  🧱 Данные / API
```

Каждый модуль — это раздел меню, внутри которого существующие экраны становятся вкладками/подпунктами. URL существующих экранов можно не менять (сохранить обратную совместимость), меняется только навигация и добавляются новые «обложки» модулей.

### Шапка каждого модуля (новый блок, единый для всех)
Три поля + статус: **Чья боль** (кресло) · **Боль** · **Действие из экрана**. Тексты — взять из `Retivo_модули_демо.html` как есть. Оформление — существующими элементами CRM (обычные карточки-плашки, как на `/overview`), без нового стиля.

### 3.3 🎁 Бонус-экономика (самые большие правки — по ТЗ Bonus Analytics)
| Что | Откуда | Правки |
|---|---|---|
| Бонусы: эффект | `/bonus` | Реструктурировать экран, см. ниже |
| Бонус-выдачи и списания | `/analytics#cash` (часть) | Перенести бонусную часть «Денег» сюда |

**Новая структура экрана (сверху вниз):**
1. **KPI-строка Bonus P&L** (7 плашек): Bonus Issued · Bonus Cost · Incremental Deposits · GGR · NGR · ROI · Retention Uplift. У каждой плашки бейдж доступности: `считается` / `частично` / `нужно событие`. Сегодня считаются: Issued (59.9 Mn ₺, ~61 000 выдач), NGR (= GGR − бонусы), Incremental/Uplift (+1.4 п.п., propensity-matching). НЕ считаются (нет данных): Bonus Cost (конвертация в реал), ROI.
2. **Воронка бонуса** — таблица этапов со статусом данных: Выдан ✅ → Активирован ❌ → Вейджер начат ❌ → Вейджер выполнен ❌ → Конвертирован/сгорел ⚠️ (косвенно: списания 22.5 Mn) → Депозит после (14д) ✅ → Остался играть (30д) ✅. Красные строки показывать с пометкой «ждёт события API» — это честно и продаёт спецификацию клиенту.
3. **Блок Incremental** (существующий): сырая разница +33 п.п. vs честная +1.4 п.п., CI [−0.7; +4.0]. Не трогать математику, только оформление.
4. **Таблица по типам бонусов** (существующая): freespins 36 938 выдач / 5.9% деп / 85.2% остались; deposit-match 5 706 / 57.1% / 99.1%; cashback 356 / 52.2% / 95.8%; no-deposit 4 109 / 7.5% / 91.5%. После появления событий добавить колонки Activated / Wagering / NGR / ROI.
5. **Фильтры**: Дата · Тип бонуса · Кампания/промокод · Аффилиат · Сегмент/VIP-тир. GEO и Brand — заглушки до гео-полей и мультибренда.
6. **Счётчик Bonus Abuse** — ссылка в модуль Риск (архетип «бонусник»: 3 426 игроков, 5% депозиторов).

Добавить в спецификацию API для казино (дополняет файл «для ЦРМ», где раздел «Бонусы» отсутствует):

```
bonus_claimed        — игрок забрал бонус

wagering_progress    — прогресс отыгрыша (x из y)
wagering_completed   — вейджер выполнен
```

Без них невозможны: воронка бонуса, Bonus Cost, ROI, детект «аномально быстрого вейджера». Отправить список Василию/Соломону для включения в спецификацию.

## 4.1 Требования к новым блокам UI (в текущем дизайне)

**Стили.** Новые блоки собирать ТОЛЬКО из существующих CSS-переменных и компонентов CRM (`--primary`, `--ink`, `--steel`, `--hair`, `.scard`, `.pill`, таблицы и т.д.). Никаких новых цветов, шрифтов и библиотек. Если нужного компонента нет — использовать ближайший существующий.

**Состояния.** Каждый новый экран/блок обрабатывает четыре состояния (не пустой экран):
- **loading** — скелетон или «считаем…» в стиле текущих плашек;
- **empty** — пояснение + что сделать (пример: KPI «Bonus Cost» без событий API показывает «нужно событие bonus_converted — см. спецификацию», а не прочерк без объяснения);
- **error** — сообщение + повтор;
- **data** — обычное состояние.

Особо: лента флагов (Риск) при нуле флагов показывает «флагов нет — всё чисто, последняя проверка N мин назад»; вердикты трафика для когорт моложе 5 дней показывают «зреет · вердикт через N дн», а не пустую ячейку.

## 4.2 Правки карточки игрока (запрос Василия, звонок 13.07)

1. **Бонусы с разбивкой по статусам.** Сейчас в карточке общее «бонусов выдано». Нужно: выдан / активирован / отыгран / не отыгран / сгорел + фильтр по типу и периоду. Кому: VIP-менеджер (смотрит, на что игрок реагирует, когда VIP просит бонус) и саппорт (контекст sorry-бонусов).
2. **⭐ Фильтр «максимальный баланс за период».** Два режима: (а) выбрал депозит → система показывает максимальный баланс от этого депозита до следующего; (б) произвольный период «дата-время от/до». Данные есть: в game_transactions хранится баланс до/после каждого спина. Кейс-обоснование: игрок жалуется «я у вас ничего не выигрываю» → саппорт видит «с депозита $100 на счету была десятка» — цитата Василия: «это закрывает рот и экономит компании бонусы». Пользователи: саппорт, колл-центр, VIP-менеджер.
3. Приоритет: обе правки — в этап 2 (быстрые, данные уже в системе).

## 5. Технические правки (вне модулей)

1. **Роли доступа**: минимум две — `менеджер` (всё, кроме Данные/API и ключей) и `админ` (всё). Сейчас один basic-auth `admin` на всю систему.
2. **Сменить пароль basic-auth** (текущий засвечен в переписке).
3. Названия игр вместо uuid (см. 3.5).
4. URL экранов не менять; старые пути должны продолжать работать (редиректы/алиасы при необходимости).
